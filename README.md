Вебзастосунок на TypeScript / Node.js для моніторингу та керування гібридним інвертором
**SK-5500P-48L** (родина **ISolar / EASUN SMG II**). Працює на Raspberry Pi, опитує
інвертор напряму по RS232 протоколом **Modbus RTU**, віддає мобільний вебінтерфейс і
REST/WebSocket API в локальну мережу. Дані нікуди назовні не йдуть.

## ✨ Можливості

- 📡 **Пряме опитування інвертора** по Modbus RTU (9600 бод, RS232), оминаючи хмару та застосунок SmartESS.
- 🔀 **Транспорти з автовизначенням** — serial (USB-RS232 адаптер) і mock (демо-дані, коли інвертор не підключений).
- 📱 **Мобільний вебінтерфейс** (Next.js) з живим оновленням через WebSocket і автоперепідключенням.
- 🌍 **Інтерфейс трьома мовами** — українська, російська, англійська; перемикання без перезавантаження.
- 🔒 **Безпечне керування** — типово лише читання; запис під явним розблокуванням, whitelist регістрів, автоповернення блокування, еталон налаштувань із підсвіткою розбіжностей (drift).
- 🏠 **Інтеграція з Home Assistant** через MQTT з автодискавері — сутності з'являються в HA самі, YAML писати не потрібно.
- 🔑 **Авторизація** (опційно) — вхід за паролем, HttpOnly-сесії, захист від перебору.
- 🚀 **Один скрипт деплою** — локальне збирання → rsync на Pi → рестарт systemd → health-check.

## 🗺️ Як це влаштовано

```
Інвертор ──(RS232 · Modbus RTU)── Raspberry Pi ──(WiFi/LAN)── телефон / браузер
                                       │
                       ┌───────────────┴───────────────┐
                       │  Node.js (цей проєкт)          │
                       │  ┌──────────┐  ┌────────────┐  │
                       │  │ transport│  │  protocol  │  │
                       │  │ serial   │  │ Modbus RTU │  │
                       │  │ mock     │  │ + карта SMG│  │
                       │  └──────────┘  └────────────┘  │
                       │        ┌────────────┐          │
                       │        │ HTTP + WS  │          │
                       │        └────────────┘          │
                       └────────────────────────────────┘
```

Інвертор — з родини **ISolar/EASUN SMG II** і говорить **Modbus RTU** (9600 бод, 8N1,
slave id 1 — налаштування №25 «Modbus ID» в меню). WiFi-донгл SmartESS — лише міст,
який опитує ті самі регістри і ретранслює дані в хмару; цей застосунок робить те саме
локально. Карта регістрів звірена з проєктом
[syssi/esphome-smg-ii](https://github.com/syssi/esphome-smg-ii) та живим пристроєм:
статус — регістри 201–234, аварії — 100/108 (бітові маски), налаштування — 300–343.

**Шари** (монорепо на npm workspaces):

| Шар | Де | Відповідальність |
|---|---|---|
| `shared` | `shared/src` | Спільні типи (`Snapshot`, …) і контракт керування (whitelist, довідники) — спільний для сервера та веба |
| `protocol` | `server/src/protocol` | `modbus.ts` — кадри/CRC-16/розбір відповідей; `smg.ts` — карта регістрів SMG II, декодери, сеттери |
| `transport` | `server/src/transport` | `serial` / `mock` за спільним інтерфейсом + автовизначення |
| `inverter` | `server/src/inverter.ts` | Опитування за таймером, черга команд (один порт, пейсинг 120 мс), автоперепідключення, еталон, блокування |
| `server` | `server/src/server.ts` | Express (REST + статика) і WebSocket (живий push) |
| `mqtt` | `server/src/mqtt.ts` | Публікація в MQTT з автодискавері Home Assistant |
| `web` | `web/` | Мобільний UI на Next.js; статичний експорт роздає той самий Express |

Коректність протоколу закріплена еталонними кадрами, знятими з живого інвертора
(`01 03 00 C9 00 01 54 34` → `01 03 02 00 03 F8 45`) — див. `server/scripts/selfcheck.ts`.

## 🚀 Швидкий старт (розробка)

Монорепо на npm workspaces: `shared/` (спільні типи й API-контракт), `server/` (Express +
WebSocket, Modbus-протокол) і `web/` (UI на Next.js). Розробка та збирання ведуться на
звичайній машині (не на Pi); Node ≥ 20.

```bash
git clone https://github.com/apanamaryov/sweethome.git inverter-monitor
cd inverter-monitor
npm install    # ставить залежності всіх воркспейсів разом
npm run dev    # сервер :3000 (mock-дані) + UI :3001 (Next.js, HMR)
```

Відкрий `http://localhost:3001` — у dev-режимі UI проксіює `/api/*` на сервер `:3000`
(див. `web/next.config.ts`).

Перед комітом — статична перевірка (typecheck веба + selfcheck протоколу):

```bash
npm run check
```

> `npm run check` для сервера запускає **`server/scripts/selfcheck.ts`** — це не typecheck,
> а звірка еталонних Modbus-кадрів (знятих із живого інвертора), CRC, декодерів регістрів
> і сеттерів. Ганяй його після будь-яких правок у `server/src/protocol/*`.

## 🔌 Підключення інвертора до Pi (залізо)

> Поки інвертор фізично не підключений, застосунок працює в режимі демо-даних і
> **автоматично підхопить** інвертор, щойно він з'явиться (після рестарту сервісу або
> циклу перепідключення).

1. **Вийми штатний WiFi-донгл SmartESS** з RS232-порту інвертора (RJ45-гніздо, порт
   моніторингу). Кабель DB9↔RJ45 від донгла — штатний, він підходить.
2. Підключи: **RS232-порт інвертора → кабель DB9↔RJ45 → USB-RS232 адаптер → USB Pi**.
   - ⚠️ Адаптер має бути зі **справжніми RS232-рівнями (±12 В)** — з перетворювачем
     рівнів (MAX232/SP232) на платі. Дешеві «USB-RS232» на CH340 часто виявляються
     USB-TTL (0/3.3 В) — з інвертором вони фізично несумісні: порт відкривається,
     але обмін мовчить. Перевірка мультиметром: на TX адаптера (пін 3 DB9) у спокої
     має бути **мінус 5…12 В**. Перевірений робочий варіант — кабель на FTDI FT231X
     з рівнеперетворювачем.
   - Розпіновка штатного кабелю (звірено продзвонюванням): RJ45 pin 1 → DB9 pin 2
     (TX інвертора), RJ45 pin 2 → DB9 pin 3 (RX інвертора), RJ45 pin 8 → DB9 pin 5
     (GND). Null-modem НЕ потрібен.
3. Перевір у меню інвертора налаштування №25 «Modbus ID» (типово **001** — збігається
   з `MODBUS_SLAVE_ID=1`).
4. Перезапусти сервіс: `sudo systemctl restart inverter-monitor`.
5. Перевір, що в шапці інтерфейсу статус змінився з «Демо-дані» на «Підключено · serial …».

Якщо Pi не бачить адаптер: `lsusb`, `ls -l /dev/ttyUSB*`, і права (користувач `pi` має
бути в групі `dialout`).

**Вимоги:** Raspberry Pi (перевірено на Pi 3B), **Node.js ≥ 18**; для збирання нативного
модуля serialport — `git`, `gcc`, `make`, `python3`.

## 📦 Деплой на Pi

Збирання — цілком **локальне**: Pi нічого не компілює, лише встановлює
production-залежності сервера та рестартує systemd-сервіс.

```bash
./deploy.sh
# з параметрами:
PI_HOST=pi@<адреса-pi> SSH_KEY=~/.ssh/<ключ> ./deploy.sh
```

Що робить скрипт:

1. `npm run build` (shared → server → web) і `npm run check`.
2. `rsync` заливає на Pi зібрані артефакти — `shared/dist`, `server/dist`, `server/systemd`, `server/.env.example`, статику `web/out` — і `package.json`/`package-lock.json` воркспейсів.
3. По SSH на Pi: ставить `npm ci -w server --omit=dev`, оновлює systemd-юніт і рестартує `inverter-monitor`.
4. Перевіряє `GET /api/health` (до хвилини на рестарт); `200` без авторизації або `401` з авторизацією — обидва означають «сервер живий».

- `PI_HOST` — користувач і адреса твого Pi (типово `pi@raspberrypi.local`).
- `SSH_KEY` — шлях до приватного ключа, якщо він не підхоплюється ssh-агентом.

На Pi конфіг і дані лежать у `server/.env` і `server/data/` (`baseline.json`, `sessions.json`);
статику роздає сам сервер із `web/out/`. Автозапуск після перезавантаження Pi
(`systemctl enable`) — разова ручна операція:

```bash
ssh pi@<адреса-pi> sudo systemctl enable inverter-monitor
```

| Змінна | Типово | Опис |
|---|---|---|
| `PORT` | `3000` | Порт HTTP/WS сервера |
| `HOST` | `0.0.0.0` | Інтерфейс прослуховування |
| `INVERTER_TRANSPORT` | `auto` | `auto` / `serial` / `mock` |
| `INVERTER_SERIAL_DEVICE` | — | Шлях до serial-пристрою (інакше автопідбір) |

| `MODBUS_SLAVE_ID` | `1` | Modbus-адреса інвертора (меню №25) |
| `POLL_INTERVAL_MS` | `5000` | Період опитування |
| `COMMAND_TIMEOUT_MS` | `3000` | Таймаут команди |
| `ALLOW_MOCK` | `true` | Демо-дані, якщо інвертор не знайдено |
| `ALLOW_CONTROL` | `true` | Мастер-вимикач запису. `false` = лише читання назавжди (розблокувати не можна) |
| `STARTUP_LOCKED` | `true` | Стартувати в режимі «лише читання» (запис потребує явного розблокування) |
| `AUTO_RELOCK` | `true` | Автоматично повертати блокування після кожного успішного запису |
| `DATA_DIR` | `data` | Куди зберігати еталон налаштувань (`baseline.json`) |
| `AUTH_PASSWORD` | — | Пароль входу в UI/API. Порожньо = без авторизації (довірена LAN) |
| `AUTH_SESSION_TTL_DAYS` | `30` | Термін життя сесійної cookie |
| `MQTT_URL` | — | Адреса MQTT-брокера (`mqtt://user:pass@host:1883`). Порожньо = MQTT вимкнено |
| `MQTT_ENABLE_CONTROL` | `false` | Керовані сутності в HA (в обхід UI-блокування) |

Повний список MQTT-змінних — у [`server/.env.example`](server/.env.example).

### 🔑 Авторизація

За заданого `AUTH_PASSWORD` весь UI, API і WebSocket вимагають входу (сторінка `/login`,
HttpOnly-cookie, сесії переживають рестарт — `server/data/sessions.json` зберігає лише SHA-256
токенів). Після 5 неправильних паролів з однієї IP — блокування на 10 хвилин.

> **Перед пробросом порту на роутері** обов'язково задай `AUTH_PASSWORD`. Голий HTTP назовні
> віддає пароль і cookie відкритим текстом — ззовні краще заходити через VPN (WireGuard) або
> reverse proxy з TLS (caddy/nginx + Let's Encrypt).

## 🖥️ Вебінтерфейс

- **Шапка** — статус підключення (Підключено / Демо-дані / Немає зв'язку), поточний режим (Від мережі / Від батареї / Байпас / Заряд / …), час останнього оновлення.
- **Батарея** — заряд (SoC, кільце), напруга, струм заряду/розряду, стан.
- **Сонце (PV)** — потужність, напруга, струм.
- **Навантаження** — активна потужність, повна (ВА), % завантаження, напруга/частота.
- **Мережа** — напруга, частота, температура інвертора.
- **Поточні налаштування та еталон** — таблиця «Зараз / Еталон» із підсвіткою розбіжностей (включно з SOC-порогами для літієвих батарей), перемикачі-функції, кнопка «Перечитати еталон».
- **Керування** — статус блокування та кнопка «Розблокувати/Заблокувати»; пріоритет джерела виходу, пріоритет заряду, макс. струм заряду, макс. струм заряду від мережі. Кожна зміна — з підтвердженням, після запису блокування повертається автоматично.
- **Діагностика** — читання/запис довільних Modbus-регістрів (`R 201 10`, `W 331 1`).

Оновлення — в реальному часі через WebSocket з автоперепідключенням.

## 🌐 API

| Метод | Шлях | Призначення |
|---|---|---|
| `POST` | `/api/login` | `{password}` — вхід, ставить сесійну cookie |
| `POST` | `/api/logout` | Вихід, відкликає сесію |
| `GET` | `/api/health` | Перевірка живості |
| `GET` | `/api/snapshot` | Поточний знімок (статус, режим, налаштування, попередження) |
| `GET` | `/api/meta` | Довідники значень для керування |
| `POST` | `/api/control` | `{type, value}` — записати налаштування (whitelist; відхиляється при блокуванні) |
| `POST` | `/api/lock` | `{locked}` — увімкнути/зняти блокування запису |
| `GET` | `/api/baseline` | Еталон налаштувань, знятий при підключенні |
| `POST` | `/api/baseline/recapture` | Свіже читання налаштувань і перезапис еталона |
| `POST` | `/api/raw` | `{command}` — Modbus напряму: `"R <адреса> [кількість]"` читає завжди, `"W <адреса> <значення>"` потребує знятого блокування |
| `WS` | `/ws` | Push знімків у реальному часі |

Типи для `/api/control`: `outputSourcePriority` (регістр 301), `chargerSourcePriority` (331),
`maxChargingCurrent` (332), `maxAcChargingCurrent` (333), `batteryRechargeVoltage` (327),
`batteryRedischargeVoltage` (326).

```bash
curl -X POST http://<адреса-pi>:3000/api/control \
  -H 'Content-Type: application/json' \
  -d '{"type":"chargerSourcePriority","value":3}'   # 3 = Only PV
```

## 🏠 Підключення до Home Assistant (MQTT)

Застосунок уміє публікувати дані в **MQTT з автодискавері Home Assistant** — HA сам створює
всі сутності. Типово інтеграція **вимкнена** (порожній `MQTT_URL`).

1. Робочий **MQTT-брокер** (зазвичай аддон **Mosquitto** в HA) і ввімкнена інтеграція **MQTT**.
2. У `server/.env` вказати брокер і перезапустити сервіс:
   ```bash
   MQTT_URL=mqtt://ha-user:ha-pass@IP-БРОКЕРА:1883
   # опційно — керування інвертором із HA (обходить UI-блокування запису):
   MQTT_ENABLE_CONTROL=true
   sudo systemctl restart inverter-monitor
   ```
3. В HA (**Налаштування → Пристрої та служби → MQTT**) з'явиться пристрій **«Inverter SK-5500P-48L»** з усіма сенсорами.

**Публікується:** сенсори PV/батареї/навантаження/мережі/температури/режиму/попереджень;
бінарні сенсори «на зв'язку», «аварія», «запис заблоковано»; за `MQTT_ENABLE_CONTROL=true` —
керовані `select` (пріоритети джерела, струми заряду).

**Топіки:** стан — `inverter/<node>/state` (JSON), доступність — `inverter/<node>/availability`,
команди — `inverter/<node>/set/<param>`, discovery — `homeassistant/<component>/<node>/<key>/config`.

> `MQTT_ENABLE_CONTROL=true` дозволяє запис із HA в обхід UI-блокування — сам прапорець і є
> усвідомлений дозвіл. Команди, як і раніше, проходять валідацію/whitelist.
>
> Сам Home Assistant на Pi 3B (~1 ГБ ОЗП) ставити не варто — це нижче рекомендованих вимог HA.
> Краще запускати HA на потужнішому вузлі; цей застосунок підключиться до нього по MQTT
> звідки завгодно в мережі.

## 🔒 Безпека керування та блокування запису

Застосунок спроєктовано за принципом **«читаємо, але не перезаписуємо, поки це не знадобиться»**:

- **Нічого не пишеться автоматично.** Опитування шле лише команди читання регістрів (fn 0x03). Запис — виключно за явною дією.
- **Блокування запису ввімкнено типово** (`STARTUP_LOCKED=true`). Поки не натиснеш «Розблокувати» (або не викличеш `POST /api/lock`), будь-які записи відхиляються — і через UI, і через API (включно з `W`-командами в `/api/raw`).
- **Автоповернення блокування** після кожного успішного запису (`AUTO_RELOCK=true`).
- **Еталон налаштувань** — за першого підключення всі поточні налаштування (регістри 300–343) один раз зчитуються та зберігаються на диск. В інтерфейсі видно **підсвітку розбіжностей** (drift). За підключення іншого пристрою еталон захоплюється заново.
- **Читання безпечне, запис — ні.** Змінюючи пороги напруг, струми заряду та пріоритети, можна нашкодити батареї чи навантаженню. Змінюй по одному параметру.
- Всі записи проходять через **whitelist регістрів** із валідацією значень; помилка запису = Modbus-виключення від інвертора.
- Повна незворотна заборона запису — `ALLOW_CONTROL=false` (розблокувати не можна).

## 🛠️ Траблшутінг

- **«Демо-дані» замість реальних** — інвертор не знайдено. Перевір підключення (`lsusb`, `/dev/ttyUSB*`), права (`dialout`), і головне — що адаптер зі **справжніми RS232-рівнями** (мінус 5…12 В на TX у спокої; USB-TTL з інвертором не працює). Задай `INVERTER_SERIAL_DEVICE` / `INVERTER_TRANSPORT` явно.
- **Timeout на всіх запитах** — перевір Modbus ID у меню інвертора (№25, має збігатися з `MODBUS_SLAVE_ID`) і швидкість (SMG II відповідає лише на 9600).
- **CRC mismatch у логах** — биті кабель/контакти або завади. Перевір обтиск RJ45 і стик DB9.
- **Modbus exception на запис** — регістр/значення не підтримується прошивкою. Звір карту регістрів (esphome-smg-ii) через діагностику (`R <адреса>`).
- **Порт зайнятий** — активний лише один опитувач; переконайся, що штатний донгл вийнято і не запущені паралельні екземпляри.
