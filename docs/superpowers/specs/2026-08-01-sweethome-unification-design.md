# Sweethome: объединение приложений дома в одну систему — дизайн

Версия дизайна: 2026-08-01. Статус: **дизайн согласован с пользователем по секциям.**

## 1. Цель и контекст

В хозяйстве есть работающее приложение мониторинга и управления инвертором
(`inverter-monitor`, git-репозиторий `apanamaryov/sweethome`) и согласованная,
но не начатая реализация управления отоплением (спека в `rancho/heating`).
В будущем планируются управление освещением и видеонаблюдение.

Цель — объединить всё в одну систему управления домом:

- один репозиторий (`sweethome`);
- единый веб-интерфейс в дизайне, уже сделанном для инвертора;
- запуск на любой Linux-машине, минимальные требования — Raspberry Pi 3B
  (~905 МБ ОЗУ, из них свободно ~574 МБ);
- общий CLAUDE.md в корне проекта.

Эта работа — **каркас**: перестройка репозитория, единый веб с обзором дома и
разделом инвертора, общий CLAUDE.md, приведение спеки и плана отопления к новой
структуре. Реализация самого отопления — следующим заходом, по его собственному
плану, уже внутри каркаса.

## 2. Принятые решения

| Развилка | Решение |
|---|---|
| Архитектура бэкенда | **Модульный монолит**: один Node-процесс, один systemd-юнит, один порт; каждая подсистема — workspace-пакет, который хост монтирует как модуль |
| Главная страница `/` | **Обзор дома**: компактные карточки подсистем со ссылками внутрь; полные разделы — `/inverter/*`, `/heating/*`, … |
| Репозиторий | **Перестраиваем существующий `sweethome`** через `git mv` (история сохраняется); рабочая копия переименовывается в `rancho/sweethome` |
| Скоуп | **Сначала каркас**; отопление реализуется потом отдельным заходом |
| Структура монорепо | **`modules/` + `packages/`**: хост отделён от доменов, у каждого домена свой пакет и свой shared-контракт |
| Авторизация | Существующая (sessions, tokens, роли `admin`/`viewer`) становится общесистемной; `forward_auth`/`/api/authz` из спеки отопления **отменяются** |
| Plugin-система, реестры, динамическая загрузка модулей | Не делаем (YAGNI) — статический список модулей в коде хоста |

Обоснование монолита: на Pi 3B каждый лишний Node-процесс стоит 60–120 МБ ОЗУ;
одна авторизация, один WS-сервер и одна статика уже написаны; правки Caddy не
нужны вовсе. Минус — деплой/краш перезапускает всё сразу — осознанно принят:
ноды отопления по своему дизайну переживают смерть сервиса (лестница
деградации), а инвертор при рестарте только читает.

## 3. Структура репозитория

```
sweethome/                      ← рабочая копия: ~/work/rancho/sweethome
  package.json                  name: sweethome, workspaces, build-порядок
  CLAUDE.md                     общий: монорепо, команды, деплой, git-правила
  README.md                     обзор всей системы
  deploy.sh
  server/                       @sweethome/server — хост:
                                Express, auth/, WS, статика, монтаж модулей
  modules/
    inverter/                   @sweethome/inverter — всё инверторное:
      CLAUDE.md                 protocol/, transport/, inverter.ts, stats/,
      README.md                 mqtt.ts, REST-роутер, mcp/ (http + gateway)
    heating/                    (появится следующим заходом)
  packages/
    shared/                     @sweethome/shared — системные типы:
                                auth-контракт, контракт модуля HomeModule
    inverter-shared/            бывший @inverter/shared (types, api,
                                registers, source, settings)
    inverter-mcp/               бывший @inverter/mcp
    heating-shared/             (позже)
  web/                          единый Next.js (App Router, static export)
  docs/
    heating/SPEC.md             переезжает из rancho/heating, правки под монолит
    superpowers/{specs,plans}/  дизайн-доки и планы
```

- **Разрез текущего `server/`**: `auth/`, хост-часть `server.ts` и общая часть
  `config.ts` остаются в `server/`; `protocol/`, `transport/`, `inverter.ts`,
  `stats/`, `mqtt.ts`, весь `mcp/` (Streamable HTTP `/mcp` + local-gateway) и
  инверторные REST-маршруты уезжают в `modules/inverter/`. Тесты едут вместе
  с кодом.
- **Порядок сборки**: `packages/shared → packages/inverter-shared →
  packages/inverter-mcp → modules/inverter → server → web` — то же правило
  «импортируем из построенного dist», что и сейчас.
- **Пакеты переименовываются** `@inverter/*` → `@sweethome/*`.
  Имена env-переменных (`INVERTER_*`, `MQTT_*`, …) **не меняются** — меньше
  риска сломать конфигурацию на Pi.
- **CLAUDE.md двухуровневый**: корневой — общесистемный; инверторная специфика
  (Modbus, write-safety, регистры, железо) — в `modules/inverter/CLAUDE.md`.
  Claude Code подхватывает вложенные CLAUDE.md автоматически.
- Папка `rancho/heating` после переезда спеки упраздняется;
  `rancho/inverter-monitor` переименовывается в `rancho/sweethome`.

## 4. Хост и контракт модуля

Контракт — интерфейс в `@sweethome/shared`, реализация у каждого модуля:

```ts
interface HomeModule {
  id: string;                      // 'inverter', 'heating', …
  apiRouter: express.Router;       // хост монтирует на /api/<id>/*
  attachWs?(server, path): void;   // WebSocket на /ws/<id>
  start(): Promise<void>;          // фоновая работа: поллинг, MQTT
  stop(): Promise<void>;           // корректная остановка (SIGTERM)
  health(): ModuleHealth;          // статус для /api/health
}
```

Хост держит **статический список модулей в коде**
(`const modules = [createInverterModule(cfg)]`). Добавление подсистемы =
новый пакет + одна строка в списке.

**Маршруты:**

| Было | Станет |
|---|---|
| `/api/status`, `/api/control`, `/api/stats/*`, `/api/raw`, `/api/lock`, `/api/baseline/*`, … | `/api/inverter/...` (имена внутри не меняются) |
| `/api/login`, `/api/me`, `/api/change-password`, `/api/users`, `/api/tokens`, `/api/health` | без изменений — системный уровень |
| `/ws` | `/ws/inverter` |
| `/mcp` | без изменений: пока это MCP инвертора; общий MCP всех модулей — потом |

- **Авторизация не меняется по сути**: та же middleware (cookie → Bearer), те
  же глобальные роли `admin`/`viewer`, те же scope'ы токенов. Она стоит перед
  `/api/*` целиком, включая все будущие модули. `forward_auth` и `/api/authz`
  из спеки отопления не нужны; конфиг Caddy не трогаем.
- **Write-safety модель инвертора** (`ALLOW_CONTROL`, lock, whitelist, аудит
  записей) — целиком внутри модуля, хост про неё не знает.
- **`/api/health`** агрегирует `health()` всех модулей:
  `{ ok, modules: { inverter: { … } } }`. Деплой-скрипт и uptime-kuma ходят на
  тот же URL, что и раньше.
- **Отказ модуля**: исключение в `start()` или фоновом цикле ловится, модуль
  помечается unhealthy и виден в `/api/health` и на обзоре дома; процесс
  продолжает жить. Полный краш процесса — как сейчас, systemd `Restart=always`.

## 5. Данные и конфигурация

- `server/data/auth.db` — системная база (пользователи, сессии, токены).
- Модульные данные — в подкаталогах: `server/data/inverter/{stats.db,
  baseline.json}`, потом `server/data/heating/heating.db`.
- Конфиг — один `server/.env`, как сейчас; модуль получает свои переменные при
  создании. Имена переменных не переименовываются.

## 6. Веб

Один Next.js (App Router, static export), отдаётся хостом с `:3000`.

| Путь | Что там | Роль |
|---|---|---|
| `/` | Обзор дома | любая |
| `/inverter` | бывший дашборд инвертора | любая |
| `/inverter/stats` | бывший `/stats` | любая |
| `/inverter/settings`, `/inverter/diagnostics` | как сейчас | `admin` |
| `/users` | пользователи и API-токены — общесистемная | `admin` |
| `/login`, `/change-password` | как сейчас | открытые |
| `/heating/*` | следующим заходом | |

- **Обзор дома (`/`)** — сетка карточек подсистем. На старте карточка одна,
  инвертор: источник питания (badge), SOC, мощность нагрузки, PV; клик ведёт в
  `/inverter`. Карточка живёт на том же WebSocket `/ws/inverter` через
  существующий `snapshot.tsx` — отдельного агрегирующего API для обзора не
  делаем, пока модулей мало. Заглушки будущих подсистем не рисуем.
- **Шапка двухуровневая**: верхний уровень — разделы (Обзор / Инвертор, позже
  + Отопление…), LangSwitch, пользователь, выход; внутри раздела — вторичные
  вкладки (у инвертора: дашборд / статистика / настройки / диагностика),
  видимость по роли как сейчас.
- **Дизайн и код UI**: существующие компоненты (`Panel`, `BatteryRing`,
  `TimeChart`, тосты, диалоги) и стили остаются в `web/components` — они и есть
  «единый дизайн»; отопление будет строиться из них же. Отдельную ui-библиотеку
  не выделяем: веб один.
- **i18n**: та же система (UA/RU/EN, типизированный словарь), один словарь на
  приложение; добавляются ключи обзора и навигации, инверторные ключи не
  переименовываются.
- **Совместимость закладок**: Express на хосте отдаёт 301-редиректы со старых
  страниц (`/stats` → `/inverter/stats`, `/settings` → `/inverter/settings`,
  `/diagnostics` → `/inverter/diagnostics`).
- **Роль `viewer`**: обзор, `/inverter`, `/inverter/stats` — та же логика
  ограничений, что сейчас, с новыми путями.

## 7. Деплой и миграция на Pi

- **deploy.sh**: механика прежняя (локальная сборка → `npm run check` → rsync
  артефактов → `npm ci --omit=dev` на Pi → рестарт systemd → health-check),
  список rsync обновляется под новую раскладку (`packages/*/dist`,
  `modules/*/dist`, `server/dist`, `web/out`, манифесты). Pi не компилирует.
- **systemd и каталог**: `inverter-monitor.service` → `sweethome.service`,
  `/home/pi/inverter-monitor` → `/home/pi/sweethome`. Одноразовая миграция —
  идемпотентный блок в deploy.sh (по образцу существующего): остановить старый
  юнит, перенести каталог, разложить `server/.env` и `server/data/*` по новой
  схеме, установить и включить новый юнит.

**Что снаружи не меняется:**

| Потребитель | Почему не ломается |
|---|---|
| Caddy (`rancho.network` → `localhost:3000`) | порт и хост те же |
| uptime-kuma | тот же `/api/health` |
| Home Assistant / MQTT discovery | `mqtt.ts` переезжает как есть, топики не меняются |
| Секреты на Pi (`server/.env`) | имена переменных не переименовываются |
| API-токены | auth не меняется, токены живы |

**Что правится на нашей стороне:** MCP stdio (`HttpGateway`) — REST-пути
инвертора переезжают под `/api/inverter/*`; обновляется в том же PR. Эндпоинт
`/mcp` и токен прежние, конфиги MCP-клиентов трогать не нужно.

## 8. Документы

- **Корневой CLAUDE.md** — из inverter-monitor, обобщается: система, команды
  монорепо, порядок сборки, деплой, git-правила, язык коммитов.
- **`modules/inverter/CLAUDE.md`** — инверторная специфика: Modbus,
  write-safety, регистры, железо, детали деплоя, касающиеся инвертора.
- **README**: корневой — обзор системы и модулей; детальный инверторный README
  переезжает в `modules/inverter/README.md`, пути API в нём обновляются.
- **Спека отопления** → `docs/heating/SPEC.md`. Меняются ровно три решения:
  «отдельное приложение и репозиторий» → модуль монолита; «forward_auth в
  Caddy» → обычная auth-middleware хоста (§10 спеки сильно упрощается); «свой
  Next.js c basePath /heating на :3002» → раздел единого веба. Содержательное —
  MQTT-контракт, лестница деградации, железо, прошивки, матрица отказов — не
  трогается. План реализации отопления обновляется под новые пути и workspaces.

## 9. Тестирование и критерии приёмки

- Все существующие jest-тесты переезжают вместе с кодом; `npm run check` /
  `npm test` агрегируют по всем workspace'ам.
- Обновляются: `server.http.test.ts` (системные пути, `/api/inverter/*` за
  auth, 301-редиректы), тесты MCP-гейтвея (новые пути), web-тесты (новые
  маршруты).
- Новое: тесты хоста — монтаж модулей, агрегация `/api/health`, изоляция отказа
  модуля; тесты обзора дома и двухуровневой шапки.

Критерии приёмки:

1. `npm run build`, `npm run check`, `npm test` зелёные.
2. В dev-режиме (mock-транспорт) работают обзор дома и раздел инвертора,
   включая управление, статистику и переключение языков.
3. После деплоя на Pi: живой инвертор виден, управление работает, статистика
   пишется, HA-интеграция и MCP отвечают, uptime-kuma зелёный.
4. Старые URL страниц редиректят на новые.

## 10. Порядок работ в git

Feature-ветка `feat/sweethome-unification`, серия осмысленных коммитов:
перенос через `git mv` → переименование пакетов и импортов → разрез
хост/модуль → веб-маршруты → deploy.sh + systemd → документы. PR в `main`,
мерж только после явного подтверждения пользователя. После мержа — деплой на
Pi и проверка вживую.

## 11. Вне скоупа

- Реализация отопления — следующий заход по его собственному плану.
- Общий MCP с инструментами всех модулей — когда появится второй модуль с
  инструментами.
- Освещение и видеонаблюдение. Про видео на будущее: скорее всего это будет
  отдельный тяжёлый сервис (типа Frigate) рядом с монолитом, интегрированный на
  уровне UI и auth; выбранный каркас этому не мешает.
- Агрегирующий API/WS для обзора дома — вернуться к вопросу, когда модулей
  станет ≥4 и по сокету на модуль станет заметно.
- Redirect'ы/совместимость старых REST-путей для внешних потребителей — кроме
  MCP-гейтвея таких потребителей нет.
