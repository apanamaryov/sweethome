# Видеонаблюдение (модуль `cctv`) — дизайн

Версия дизайна: 2026-08-24. Статус: **дизайн согласован с пользователем по секциям.**

## 1. Цель

Своё видеонаблюдение в обход облака производителя камер: круглосуточная запись на
локальный диск, живой просмотр и просмотр архива с нормальной перемоткой — всё
внутри уже существующего веб-интерфейса `sweethome`.

Камеры сейчас работают только через приложение V380 Pro и облако вендора. Записи
хранятся у производителя, доступа к ним из своей сети нет.

## 2. Результаты разведки железа

Всё ниже — **измерено на месте 2026-08-24**, не предположения.

### 2.1 Камеры

| | |
|---|---|
| Модель | ONVIF-идентификация: `macro-video-soft IPCamera`, прошивка `2.4` |
| Найдено в сети | `192.168.1.93`, `192.168.1.115` (третья камера в сети не отвечала — вне скоупа v1) |
| Открытые порты | `554` (RTSP), `8800`, `8899` (ONVIF), `9800` |
| RTSP | Работает **без авторизации**; `rtsp://<ip>:554/live/ch00_0` — основной поток, `live/ch00_1` — экономный |
| Пути RTSP | Камера отдаёт основной поток по **любому** пути, кроме `live/ch00_1`; полагаемся на `live/ch00_0` |
| Разрешение | **1920×2160** — две линзы, склеенные камерой в один кадр (верх/низ). Один поток на камеру, не два |
| Кодек | Был H.265, **переключён пользователем на H.264** через приложение V380 Pro (Main, `profile-level-id=TQAy` → `avc1.4d0032`) |
| Кадры | ~14 fps, опорные (ключевые) кадры **раз в ~2.9 с** |
| Битрейт | 680–870 кбит/с видео (в H.264; на H.265 было 520–670) + ~16 кбит/с звук (AAC 8 кГц). Потолок по настройке камеры — 2048 кбит/с |
| Экономный поток | 640×720, ~730 кбит/с (после перехода на H.264 стал не сильно дешевле основного — смысла в нём мало) |

**Особенность упаковки потока.** Камера склеивает `SPS + PPS + IDR` в один NAL-юнит и
фрагментирует его с заголовком типа 7 (SPS) вместо 5 (IDR). Строгие декодеры
(проверено: `gstreamer` + `rtph264depay`) не распознают начало опорного кадра и
показывают серый мусор вместо картинки. **ffmpeg это переваривает корректно** —
запись и извлечение кадров проверены, картинка чистая. Из этого следует
архитектурное ограничение: **весь приём и разбор видео в модуле идёт только через
ffmpeg**; переход на gstreamer или самописный RTP-разбор потребует отдельного
исследования.

### 2.2 ONVIF

- Порт `8899`, сервисы: `device`, `media`, `imaging`, `events`, `ptz`.
- **Чтение работает без авторизации** (`GetCapabilities`, `GetProfiles`,
  `GetVideoEncoderConfiguration`, `GetEventProperties`).
- **Запись настроек не работает вообще.** `SetVideoEncoderConfiguration` отвечает
  `ter:InvalidArgVal / ter:ConfigModify` даже при попытке сохранить **ровно те
  настройки, что уже стоят** (проверено контрольным тестом). Менять кодек, битрейт
  и fps можно только из приложения V380 Pro. Модуль не должен пытаться настраивать
  камеры по ONVIF.
- `GetSnapshotUri` — таймаут, снимков камера не отдаёт. Превью придётся получать
  своим декодированием, если понадобится.
- **События (PullPoint) работают**: подписка создаётся, сообщения доставляются
  (получены `ImageTooDark`, `ImageTooBlurry`). В списке топиков объявлен
  `tns1:VideoSource/MotionAlarm`, но **за 5 минут наблюдения ни одного события
  движения не пришло** — см. §10 и §20.

### 2.3 Хранилище

| | |
|---|---|
| Диск | SSD, подключён к роутеру Keenetic (`192.168.1.1`), раздаётся по SMB как `//192.168.1.1/backup` |
| Объём | 916 ГБ, занято 537 МБ (бэкапы, каталог `robot/`) |
| Квота под видео | **500 ГБ** (решение пользователя) |
| Текущее монтирование на Pi | `/mnt/rancho-backup`, `noauto` + `uid=0,gid=0,file_mode=0600,dir_mode=0700` — **только root, только по требованию** |
| Скорость через Wi-Fi | запись **2.8 МБ/с** (~22 Мбит/с), чтение 4.7 МБ/с (~38 Мбит/с) |

### 2.4 Малина

Raspberry Pi 3B, 905 МБ ОЗУ (свободно ~500 МБ), Debian 13 trixie arm64, Node 24,
сеть — **только Wi-Fi 2.4 ГГц** (Ethernet не подключён), система на SD-карте 14.6 ГБ
(свободно 9.1 ГБ). `ffmpeg` **не установлен**.

### 2.5 Проверка нагрузки под реальной записью

Три минуты записи двух камер одновременно (`-c copy`, минутные сегменты, вывод на
SMB-диск роутера):

| | |
|---|---|
| Ошибок | ноль |
| Процессор | занято ~10% всего (сам ffmpeg 0–8%, остальное — системная работа с сетью) |
| Память | ~20 МБ на процесс, +40 МБ на обе камеры |
| Load average | 0.23 |
| Трафик | 8.5 МБ/мин суммарно = **1.1 Мбит/с**, то есть **5%** от пропускной способности канала |
| Объём | cam93 ≈ 4.55 МБ/мин, cam115 ≈ 3.96 МБ/мин → **12.2 ГБ/сутки** на обе камеры |

**Вывод:** 500 ГБ ≈ **40 суток** архива при дневном битрейте. Ночью (инфракрасная
подсветка даёт шум) расход вырастет, реалистичная оценка — **3–6 недель**. Тянуть
Ethernet или переносить запись на роутер не требуется: запаса по каналу и
процессору многократный.

## 3. Принятые решения

| Развилка | Решение |
|---|---|
| Куда встраивается | Новый модуль `modules/cctv` в существующем монолите: `apiRouter` на `/api/cctv`, WS на `/ws/cctv`, данные в `server/data/cctv/`, страницы `/cctv/*` |
| Приём видео | **Только ffmpeg**, `-c copy`, без перекодирования (см. §2.1 про упаковку потока) |
| Формат хранения | **Фрагментированный MP4** (fMP4): сегменты `.m4s` + отдельный init-сегмент. Обычный MP4 непригоден — не склеивается в непрерывную ленту |
| Длина сегмента | **60 секунд** (~4 МБ). Компромисс: точность перемотки всё равно ограничена опорными кадрами (~3 с), а более мелкие файлы плодят десятки тысяч записей на медленном SMB |
| Раскладка файлов | Один каталог на камеру, дата и время в имени файла. **Без** ротации каталогов по суткам — иначе пришлось бы перезапускать ffmpeg в полночь и получать разрыв в записи каждые сутки |
| Индекс | SQLite `server/data/cctv/index.db` (`node:sqlite`, как статистика инвертора). Поиск по времени идёт по индексу, а не обходом каталога на SMB |
| Живой просмотр | **По требованию**: отдельный процесс ffmpeg на камеру, fMP4-фрагменты идут в браузер по WebSocket, собираются через MediaSource. Задержка ~1 с, старт до 3 с (ждём опорный кадр). Процесс гаснет через 15 с после уходa последнего зрителя |
| Просмотр архива | Плейлист HLS, **генерируемый из индекса** на запрошенный интервал, + `hls.js` в браузере. Непрерывная лента, перемотка по всему интервалу, разрывы видны как разрывы |
| Кадр 1920×2160 | **Не режем** — показываем как камера отдаёт (решение пользователя) |
| Хранилище | Отдельная точка монтирования только под видео, чтобы не менять права работающего бэкап-монтирования |
| Квота | Своя, **500 ГБ**, считается по индексу; при подходе к пределу удаляются самые старые сегменты. Свободное место диска — не критерий (рядом живут бэкапы) |
| Доступ | `admin` **и** `viewer` — обе страницы и всё API модуля (решение пользователя) |
| Настройка камер | Конфиг модуля (имя + адрес). Добавление третьей камеры = одна строка |
| Настройка камер по ONVIF | **Не делаем** — камера не даёт писать настройки (§2.2) |
| Буферизация при отвале диска | **Не делаем.** 12 ГБ/сутки на SD-карту убьют её за месяцы; разрыв в архиве честно показывается на ленте |
| Умная детекция (человек/машина) | **Вне скоупа** — Pi 3B с 1 ГБ ОЗУ это не потянет |

## 5. Запись

На каждую камеру — свой процесс:

```
ffmpeg -nostdin -hide_banner -loglevel error \
  -rtsp_transport tcp -use_wallclock_as_timestamps 1 \
  -i rtsp://<ip>:554/live/ch00_0 \
  -c copy \
  -f hls -hls_time 60 -hls_list_size 0 \
  -hls_segment_type fmp4 \
  -hls_fmp4_init_filename init_<runId>.mp4 \
  -hls_flags append_list+program_date_time+independent_segments+temp_file \
  -hls_segment_filename '<dir>/seg_%Y%m%d_%H%M%S.m4s' -strftime 1 \
  <dir>/live.m3u8
```

Почему так:

- `-c copy` — ни декодирования, ни кодирования; проверено, что процессор при этом
  практически свободен.
- `-rtsp_transport tcp` — обязательно: по UDP поток на этой сети не поднимался.
- `-use_wallclock_as_timestamps 1` — камера не проставляет временные метки
  (ffmpeg предупреждает `Timestamps are unset`); без этого сегменты получают
  некорректную длительность.
- `hls_segment_type fmp4` — фрагментированный MP4, тот же формат, что и в живом
  просмотре: один тип данных на обе задачи.
- `program_date_time` — в плейлист попадает реальное время начала сегмента; это
  первоисточник для индекса.
- `temp_file` — файл появляется под финальным именем только целиком, поэтому
  сканер не подхватит недописанный сегмент.
- `init_<runId>.mp4` — **уникальное имя init-сегмента на каждый запуск** процесса.
  Если камера когда-нибудь сменит параметры потока (например, пользователь опять
  переключит кодек в приложении), новый init не сломает воспроизведение старых
  сегментов: каждый сегмент в индексе знает свой init.

**Надзор за процессом.** Модуль следит за процессом и перезапускает его при
падении с нарастающей паузой (1 с → 2 → 5 → 10 → 30, дальше каждые 30 с), сбрасывая
счётчик после минуты успешной работы. Причины падений в норме: обрыв Wi-Fi,
перезагрузка роутера, недоступность камеры, отвал SMB-монтирования.

## 6. Хранилище

```
/mnt/cctv/                     отдельная точка монтирования (только видео)
  cam-<id>/
    init_<runId>.mp4
    seg_20260824_183334.m4s
    seg_20260824_183434.m4s
    live.m3u8                  служебный плейлист ffmpeg, источник для индекса
```

Отдельная точка вместо существующей `/mnt/rancho-backup`: у той намеренно строгие
права (`root`, `0600`) под бэкапы, и менять их ради видео неправильно. Новая точка
монтирует **подкаталог** той же шары с правами пользователя, под которым работает
`sweethome`.

**Чистка (retention).** Раз в 10 минут: суммарный размер по индексу сравнивается с
квотой (500 ГБ по умолчанию, настраивается). При превышении удаляются самые старые
сегменты — файл, затем запись в индексе; init-сегмент удаляется, когда на него не
осталось ссылок. Порог срабатывания — 98% квоты, чистим до 95%, чтобы не дёргать
диск на каждой итерации.

## 7. Индекс

`server/data/cctv/index.db`, три таблицы:

```sql
CREATE TABLE inits (
  id       INTEGER PRIMARY KEY,
  cam      TEXT NOT NULL,
  path     TEXT NOT NULL UNIQUE,     -- относительно корня хранилища
  bytes    INTEGER NOT NULL,
  created  INTEGER NOT NULL          -- unix ms
);

CREATE TABLE segments (
  id       INTEGER PRIMARY KEY,
  cam      TEXT NOT NULL,
  init_id  INTEGER NOT NULL REFERENCES inits(id),
  path     TEXT NOT NULL UNIQUE,
  start_ms INTEGER NOT NULL,         -- из EXT-X-PROGRAM-DATE-TIME
  dur_ms   INTEGER NOT NULL,         -- из EXTINF
  bytes    INTEGER NOT NULL
);
CREATE INDEX idx_seg_cam_start ON segments(cam, start_ms);

CREATE TABLE motion (
  id       INTEGER PRIMARY KEY,
  cam      TEXT NOT NULL,
  ts_ms    INTEGER NOT NULL,
  kind     TEXT NOT NULL             -- 'motion' и прочие топики ONVIF
);
CREATE INDEX idx_motion_cam_ts ON motion(cam, ts_ms);
```

**Сканер** читает `live.m3u8` каждой камеры (только прирост с прошлого раза),
берёт из него `EXT-X-PROGRAM-DATE-TIME` + `EXTINF` + имя файла, добавляет записи.
Размер файла берётся из `stat`. Плейлист ffmpeg — единственный надёжный источник
длительности: из имени файла её не вычислить, а разбор самого `.m4s` — лишняя
работа.

**Восстановление.** Если индекс потерян или отстал (например, `index.db` удалён, а
файлы на месте) — полный проход по каталогу камеры: файлы, которых нет в индексе,
добавляются со временем из имени и длительностью из плейлиста, а при его
отсутствии — 60 с по умолчанию. Это аварийный путь, не штатный.

## 8. Живой просмотр

Задержка ~1 секунда достигается тем, что видео не проходит через нарезку на файлы,
а идёт в браузер потоком мелких фрагментов:

```
ffmpeg -nostdin -rtsp_transport tcp -use_wallclock_as_timestamps 1 \
  -i rtsp://<ip>:554/live/ch00_0 -an -c copy \
  -f mp4 -movflags +frag_keyframe+empty_moov+default_base_moof \
  -frag_duration 500000 pipe:1
```

- `-frag_duration 500000` (0.5 с) — фрагменты нарезаются чаще, чем идут опорные
  кадры, иначе задержка была бы равна интервалу опорных кадров (~3 с). Точное
  сочетание `frag_keyframe` и `frag_duration` подбирается на стенде отдельным шагом
  плана: это единственное место дизайна, где поведение ffmpeg на этих камерах ещё не
  проверено измерением.
- `-an` — звук в живом просмотре в v1 не отдаём (см. §19).
- Node читает `stdout`, накапливает целые фрагменты и рассылает их подписчикам
  `/ws/cctv` бинарными сообщениями. Первое сообщение каждому новому подписчику —
  начальный фрагмент с заголовком (`ftyp+moov`), он запоминается при старте
  процесса.
- Браузер: `MediaSource` + `SourceBuffer('video/mp4; codecs="avc1.4d0032")`. Кодек
  берётся из данных ONVIF/потока с этим значением как значением по умолчанию
  (измерено для этих камер).

**Жизненный цикл.** Первый подписчик поднимает процесс, последний — гасит его через
15 секунд (чтобы переход между страницами не дёргал ffmpeg). Несколько зрителей
одной камеры делят один процесс. Живой просмотр **не влияет на запись** — это
отдельное RTSP-соединение к камере.

**Отставание клиента.** Если браузер не успевает (слабая сеть), буфер
`SourceBuffer` подрезается с начала, воспроизведение перескакивает к свежему — для
живой картинки актуальность важнее непрерывности.

## 9. Архив и перемотка

**Лента.** `GET /api/cctv/timeline?cam=<id>&from=<ms>&to=<ms>` отдаёт:

- непрерывные отрезки записи (склеенные соседние сегменты, разрыв > 2 с считается
  дыркой);
- метки движения за интервал (если они есть, §10);
- суммарный размер и число сегментов.

Из этого рисуется шкала: закрашенные участки — есть запись, пустые — нет.

**Воспроизведение.** `GET /api/cctv/playlist.m3u8?cam=<id>&from=<ms>&to=<ms>` собирает
плейлист **из индекса**, а не с диска:

```
#EXTM3U
#EXT-X-VERSION:7
#EXT-X-TARGETDURATION:60
#EXT-X-PLAYLIST-TYPE:VOD
#EXT-X-MAP:URI="/api/cctv/init/12"
#EXT-X-PROGRAM-DATE-TIME:2026-08-24T18:33:34.000Z
#EXTINF:60.0,
/api/cctv/segment/84213
...
#EXT-X-ENDLIST
```

- `PLAYLIST-TYPE:VOD` — плеер знает всю длину заранее, ползунок работает по всему
  интервалу.
- Разрыв в записи оформляется `EXT-X-DISCONTINUITY` + новым
  `EXT-X-PROGRAM-DATE-TIME` — плеер не считает пропущенное время записанным.
- Смена init-сегмента (после перезапуска процесса) — тоже `EXT-X-DISCONTINUITY` с
  новым `EXT-X-MAP`.
- В браузере — `hls.js` (`Media Source Extensions`, тот же механизм, что у живого
  просмотра).

**Выдача файлов.** `GET /api/cctv/segment/:id` и `/api/cctv/init/:id` отдают файлы с
хранилища с поддержкой `Range` (нужна для перемотки внутри сегмента) и длинным
`Cache-Control` — сегменты неизменяемы. Путь к файлу берётся **из индекса по
числовому id**; имя файла из запроса не используется вовсе — это исключает выход за
пределы каталога хранилища.

**Скачивание куска.** `GET /api/cctv/download?cam=<id>&from=&to=` склеивает нужные
сегменты в один MP4 (`ffmpeg -f concat -c copy`, без перекодирования) и отдаёт
файлом. Интервал ограничен сверху (по умолчанию 30 минут), чтобы случайный запрос
на сутки не занял малину и канал надолго.

## 10. Метки движения

Модуль держит ONVIF PullPoint-подписку на каждую камеру и пишет в таблицу `motion`
события с топиком `tns1:VideoSource/MotionAlarm` (`State=true`). Подписка живёт
циклом: `CreatePullPointSubscription` → `PullMessages` с таймаутом → повтор;
падение подписки не влияет ни на запись, ни на просмотр.

**Статус на 2026-08-24: не подтверждено.** Топик камерой объявлен, механизм
доставки событий работает, но за 5 минут наблюдения ни одного `MotionAlarm` не
пришло. Возможные причины: детекция движения выключена в приложении V380 Pro, либо
камера сообщает о движении только в своё облако. Требуется проверка с участием
пользователя (§20).

Поэтому эта часть спроектирована **отключаемой**: если событий нет, лента
показывается без меток, всё остальное работает как есть. Никакая другая функция от
меток не зависит.

## 11. API

Всё под `/api/cctv`, доступно `admin` и `viewer`; чтение — без скоупа `write`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/cameras` | список камер: id, имя, разрешение, статус записи, время последнего сегмента |
| GET | `/timeline?cam&from&to` | отрезки записи, разрывы, метки движения |
| GET | `/playlist.m3u8?cam&from&to` | плейлист для плеера (§9) |
| GET | `/segment/:id` | файл сегмента (`Range`, кэшируемый) |
| GET | `/init/:id` | init-сегмент |
| GET | `/download?cam&from&to` | склейка интервала в MP4 |
| GET | `/storage` | занято, квота, глубина архива, состояние монтирования |
| WS | `/ws/cctv` | живой просмотр: `{type:"subscribe",cam}` / `{type:"unsubscribe",cam}`, в ответ бинарные фрагменты |

`health()` модуля возвращает: по каждой камере — пишем/не пишем, число
перезапусков, время последнего сегмента; плюс доступность хранилища и наличие
`ffmpeg`.

## 12. Веб-интерфейс

**`/cctv` — живой просмотр.** Две картинки, каждая с именем камеры и признаком
живого потока. При недоступности камеры — плашка с причиной вместо чёрного
квадрата. Кадр показывается как есть (1920×2160, вытянутый по вертикали): на
мобильном занимает экран естественно, на широком мониторе — столбик по центру.

**`/cctv/archive` — архив.** Выбор камеры и суток, под видео — лента времени с
ползунком, закрашенные участки = есть запись, метки движения (если появятся) —
засечками. Кнопка «скачать кусок» по выбранному интервалу.

**Карточка на `/`** (общий обзор): пишем ли сейчас, сколько занято из 500 ГБ, на
сколько суток хватает архива при текущем расходе, ссылка в раздел.

**i18n** — тексты идут в общий типизированный словарь `web/lib/i18n/dict.ts`
(UA/RU/EN), как и всё остальное в проекте.

## 13. Авторизация

Ничего нового: гейт хоста (`cookie`-сессия или `Bearer`-токен) уже стоит на `/api` и
`/ws/<id>`. Модуль не добавляет `requireAdmin` ни на один свой маршрут — доступ
`admin` и `viewer` (решение пользователя, §3). Страницы `/cctv/*` **не** попадают в
`ADMIN_PAGES` в `server/src/server.ts` и в `ADMIN_PATH_PREFIXES` в вебе.

Отдельно отмечено как осознанный риск: RTSP на камерах открыт без пароля, то есть
любой в домашней сети может смотреть камеры напрямую, минуя `sweethome`. Закрыть
это можно только со стороны камер (пароль в приложении V380), к модулю отношения не
имеет.

## 14. Конфигурация

Через переменные окружения (`server/.env`), как у инвертора:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `CCTV_ENABLED` | `true` | выключатель модуля целиком |
| `CCTV_CAMERAS` | — | список: `drive=192.168.1.93,yard=192.168.1.115` |
| `CCTV_STORAGE_DIR` | `/mnt/cctv` | корень хранилища |
| `CCTV_QUOTA_GB` | `500` | квота |
| `CCTV_SEGMENT_SEC` | `60` | длина сегмента |
| `CCTV_FFMPEG` | `ffmpeg` | путь к бинарнику |
| `CCTV_LIVE_IDLE_SEC` | `15` | сколько живой процесс живёт без зрителей |
| `CCTV_MOTION_EVENTS` | `true` | подписка на события ONVIF |
| `CCTV_DOWNLOAD_MAX_MIN` | `30` | предел интервала для скачивания |

Модуль с `CCTV_ENABLED=false` или пустым списком камер стартует, но ничего не
делает и честно сообщает это в `health()` — чтобы `npm run dev` на машине
разработки не пытался ходить к камерам.

## 15. Подготовка малины (делается руками, один раз)

1. **Установить ffmpeg:** `sudo apt install ffmpeg`. Скрипт деплоя добавит проверку
   наличия бинарника и остановится с понятной ошибкой, если его нет.
2. **Постоянное монтирование под видео** — отдельная запись в `/etc/fstab` для
   `/mnt/cctv` с `uid`/`gid` пользователя `sweethome`, `_netdev`, автоматическим
   подключением при загрузке. Существующая запись `/mnt/rancho-backup` не меняется.
3. **Закрепить адреса камер** в Keenetic (привязка к MAC). Сейчас адреса выданы
   автоматически: после перезагрузки роутера они могут поменяться, и запись встанет.

Пункты 1 и 2 войдут в план реализации как отдельные шаги с проверками; пункт 3 —
на пользователе.

## 16. Отказы и деградация

| Что случилось | Поведение |
|---|---|
| Камера недоступна (выключена, сменился адрес) | ffmpeg падает → перезапуск с нарастающей паузой; в `health()` и в UI — «нет связи»; на ленте архива — разрыв |
| Оборвался Wi-Fi малины | то же самое; запись возобновляется сама после восстановления |
| Отвалилось SMB-монтирование (перезагрузка роутера) | запись падает; модуль проверяет доступность точки монтирования перед перезапуском и не крутит ffmpeg вхолостую; в UI — «хранилище недоступно» |
| `ffmpeg` не установлен | модуль стартует, запись не идёт, `health()` = не ok с внятной причиной; остальные модули работают |
| Диск заполнен вопреки квоте | чистка удаляет старое агрессивнее; при неудаче запись останавливается с явной ошибкой, а не пишет битые файлы |
| Индекс повреждён | восстановление сканированием каталога (§7) |
| Камера сменила параметры потока | новый init-сегмент, `EXT-X-DISCONTINUITY` в плейлисте; старый архив продолжает воспроизводиться |

## 17. Тестирование

Jest, как во всём проекте; **живые камеры не требуются**.

`modules/cctv`:

  отрезки, определение разрывов, удаление init-сегмента без ссылок.
- `index/scanner.test.ts` — разбор `live.m3u8` (`PROGRAM-DATE-TIME`, `EXTINF`),
  идемпотентность повторного прохода, дописанный «хвост» плейлиста,
  восстановление индекса по каталогу.
- `index/retention.test.ts` — чистка по квоте: что удаляется первым, порог 98/95%,
  поведение при пустом индексе.
- `playlist.test.ts` — генерация плейлиста: границы интервала, `DISCONTINUITY` на
  разрывах и на смене init, пустой интервал, ограничение длины.
- `recorder/ffmpeg.test.ts` — сборка аргументов (чистая функция) для разных
  конфигов.
- `recorder/process.test.ts` — надзор на поддельном процессе: перезапуск, backoff и
  его сброс, отказ от перезапуска при недоступном хранилище, остановка по `stop()`.
- `live/hub.test.ts` — на поддельном источнике: первый подписчик поднимает сессию,
  последний гасит её через таймаут, начальный фрагмент уходит каждому новому
  подписчику, несколько зрителей делят одну сессию.
- `router.test.ts` (`supertest`) — коды и формы ответов, доступ для `viewer`,
  валидация параметров, `Range` на выдаче сегмента, попытка обхода каталога, предел
  на `download`.
- `config.test.ts` — разбор `CCTV_CAMERAS`, значения по умолчанию, выключенный
  модуль.

`server` — `host.test.ts` уже покрывает изоляцию ошибок модулей; добавится случай
модуля `cctv` в списке.

`web` — тесты компонента ленты (расчёт отрезков и позиции ползунка — чистые
функции) и карточки обзора.

**Проверяется руками на стенде** (в план реализации отдельными шагами): живая
картинка и её задержка, перемотка по архиву, скачивание куска, поведение при
выключении камеры и при перезагрузке роутера.

## 18. Критерии приёмки

1. Обе камеры пишутся круглосуточно, разрывы только на время реальных обрывов.
2. `/cctv` показывает живую картинку с задержкой около секунды, старт — не дольше
   3 секунд.
3. `/cctv/archive` даёт непрерывную перемотку по выбранным суткам; границы минутных
   файлов на слух и на глаз не заметны.
4. Разрывы записи видны на ленте и не выдаются за записанное время.
5. Занятое место не превышает 500 ГБ; старое удаляется само.
6. `viewer` имеет доступ к обеим страницам; неавторизованный — нет.
7. Выключение камеры, обрыв Wi-Fi и перезагрузка роутера не требуют ручного
   вмешательства: запись возобновляется сама.
8. `npm run check` и `npm test` проходят; новые тесты не требуют камер.
9. Инвертор продолжает работать без изменений в поведении.

## 19. Вне скоупа v1

- Третья камера — добавляется строкой в конфиг, когда появится в сети.
- Умное распознавание («человек», «машина») — Pi 3B не потянет.
- Звук в живом просмотре (в записи звук есть).
- Управление поворотом (у камер есть ONVIF PTZ-сервис).
- Разрезание кадра на две линзы — пользователь отказался явно.
- Уведомления о движении (телеграм и прочее).
- Экономный поток камеры (после перехода на H.264 он почти не дешевле основного).

## 20. Открытые вопросы

1. **Шлют ли камеры события движения** (§10). Нужна проверка: включить
   «Обнаружение движения» в приложении V380 Pro и пройтись перед камерой. Если
   событий нет — лента без меток, остальное не меняется.
2. **Третья камера** — где она и появится ли в сети.
3. **Ночной битрейт** — измерен только дневной; глубина архива уточнится после
   первых суток работы.

## 21. Риски

| Риск | Оценка | Что делаем |
|---|---|---|
| Камеры отдают поток нестандартно, и это ломает не только gstreamer | Средний | Весь путь видео — через ffmpeg, проверено на записи и на извлечении кадров. Живой просмотр через MSE — тот же ffmpeg, но проверяется на стенде отдельным шагом плана |
| Адрес камеры сменится (DHCP) | Высокий | Закрепление в роутере (§15.3); до этого — перезапуск с backoff и явная ошибка в UI |
| SMB-диск отвалится надолго | Средний | Разрыв в архиве, восстановление автоматическое; буферизации на SD нет осознанно |
| Пользователь снова переключит кодек в приложении | Низкий | Уникальный init на запуск + `DISCONTINUITY` в плейлисте: старый архив остаётся читаемым |
| Живой просмотр «съест» малину при нескольких зрителях | Низкий | Один процесс на камеру независимо от числа зрителей; гашение по простою |
| Рост числа файлов на SMB | Низкий | Минутные сегменты (~86 тыс. файлов на месяц архива), поиск идёт по SQLite, а не обходом каталога |
