# Устойчивое окно солнечного дня (начало утром / конец вечером)

Дата: 2026-07-26. Статус: одобрено владельцем (дизайн-сессия).

## Цель

Показывать за сутки **ровно две отметки времени**:

1. **Начало** — когда с утра солнце стабильно уже начало давать энергию для заряда/питания.
2. **Конец** — когда вечером полностью прекратило её давать.

Это заменяет прежнюю дребезжащую пару событий `solar-charge-start`/`solar-charge-stop`,
которые писались на каждый переход триггера Шмитта по `pvChargingPower` (каждое
набегающее облако плодило запись). Владелец хочет не «первое/последнее срабатывание»,
а устойчивые границы светового дня, невосприимчивые к облакам и одиночным всплескам.

## Требования (зафиксированы с владельцем)

- **Сигнал** — `pvPower` (регистр 223), **вся** выработка панелей: и то, что идёт в
  заряд, и то, что напрямую питает нагрузку. Не `pvChargingPower` (224): при полной
  батарее в полдень заряд ≈ 0, хотя солнце явно «даёт энергию».
- **Одна пара в день.** Начало = первый за сутки устойчивый выход PV выше порога;
  конец = последний такой момент. Облака среди дня автоматически оказываются
  «внутри» окна и игнорируются.
- **Чувствительность — консервативная**: порог **200 Вт**, устойчивость **≥ 15 мин**.
  Значения тюнятся через env, не хардкод.
- **Где видно**: на дашборде — 2 живых поля «сегодня»; на `/stats` — 2 колонки в
  суточной таблице (история по дням).
- Старые события `solar-charge-start`/`solar-charge-stop` больше не пишем; из журнала
  (фильтр + метки) убираем. Уже накопленные строки в БД не трогаем.

## Ядро: `computeSolarWindow` (чистая функция)

Единственный источник правды и для истории, и для «сегодня». Живёт в новом изолированном
модуле `server/src/stats/solar.ts` — без БД, сети и времени внутри (для live `nowMs`
передаётся аргументом). Тестируется в отрыве.

```
computeSolarWindow(points, { thresholdW, dwellMin }, nowMs?) -> { start, end, state }
```

- `points` — поминутный ряд `{ ts, pv }` за локальные сутки, по возрастанию `ts`
  (для расчёта берётся `pvPower_avg` из `samples_minute`). `ts` — unix ms.
- `thresholdW` — порог мощности (default 200).
- `dwellMin` — устойчивость в минутах (default 15). Двойная роль: и минимальная длина
  прогона, и величина провала, начиная с которой провал считается «концом».

Алгоритм:

1. Отбираем минуты, где `pv ≥ thresholdW`.
2. Склеиваем их в **прогоны**, перешагивая под-пороговые провалы **короче `dwellMin`**
   (короткое облако не рвёт прогон). Провал ≥ `dwellMin` начинает новый прогон.
3. **Отбрасываем прогоны короче `dwellMin`** (одиночные рассветные/закатные всплески).
   Правило длины: число **надпороговых** минут в прогоне `≥ dwellMin` (именно
   надпороговых, а не полного размаха — брифные под-пороговые провалы, перешагнутые
   на шаге 2, в длину не засчитываются; так реальная выработка, рассечённая коротким
   облаком, не выпадает, а одиночный 10-минутный всплеск при `dwellMin=15` — выпадает).
4. Если уцелевших прогонов нет → `{ start: null, end: null, state: "idle" }`.
5. Иначе `start` = начало первого уцелевшего прогона, кандидат-`end` = конец последнего.

Провалы среди дня оказываются между `start` и `end` → всегда ровно одна пара.
Один параметр `dwellMin` закрывает и «сколько держаться», и «какой провал = конец».

### Состояние (live vs история)

- **Ретроспектива (`nowMs` не передан)** — сутки закрыты: `state = "ended"`,
  `end` = конец последнего уцелевшего прогона.
- **Live (`nowMs` передан)**:
  - нет уцелевших прогонов → `state = "idle"`, `start = end = null` («не началось»);
  - последний прогон дотягивает до «сейчас» (`nowMs − lastRunEnd < dwellMin`
    минут, т.е. `< dwellMin*60000` мс) → `state = "active"`, `start` задан,
    `end = null` («идёт с HH:MM»);
  - после последнего прогона уже `≥ dwellMin` минут темно → `state = "ended"`,
    `end = lastRunEnd` (`HH:MM–HH:MM`).

Осознанный компромисс live-режима: очень длинное (> 15 мин) облако среди дня временно
переведёт «сегодня» в `ended`, а с возвратом солнца — обратно в `active` с более поздним
концом. Самокорректируется; при консервативных 15 мин на продуктивном дне почти не
случается. **Значение, записанное в БД при закрытии суток, всегда корректно** —
оно считается по полному ряду.

## Данные (SQLite)

- Таблица `daily` получает два столбца: `solar_start_ts INTEGER`, `solar_end_ts INTEGER`
  (nullable, unix ms).
- **Миграция схемы `user_version 1 → 2`**: `ALTER TABLE daily ADD COLUMN …` для обоих
  столбцов + **разовый бэкофилл**: пройти по всем дням, присутствующим в `samples_minute`
  (retention 2 года), посчитать окно и проставить столбцы — чтобы история появилась
  сразу, а не начиная с завтра. Бэкофилл идёт по локальным дням (`DAY_EXPR`), для каждого
  дня — ретроспективный `computeSolarWindow` по его минуткам.
- `rollupDaily(nowMs)`: при свёртке каждого закрытого дня, помимо существующих агрегатов,
  считает окно из минуток этого дня и пишет `solar_start_ts`/`solar_end_ts`. Так как это
  требует построчного скана (не выражается в SQL агрегатом), делается в JS через
  `computeSolarWindow`, а не внутри `dailyStmt`.

## Конфиг (`server/src/config.ts`)

Новые поля в `cfg.stats` из env:

- `STATS_SOLAR_THRESHOLD_W` → `solarThresholdW`, default **200**.
- `STATS_SOLAR_DWELL_MIN` → `solarDwellMin`, default **15**.

Прокидываются в `StatsDb` (нужны и для rollup/бэкофилла, и для live-запроса) и в роут
`/api/stats/solar-window`. Дописать в `.env.example`.

## API (`server/src/server.ts`, роуты `/api/stats/*`)

- **`GET /api/stats/solar-window?day=YYYY-MM-DD`** (по умолчанию — сегодня, локальный день).
  Ответ `{ day, start, end, state }` (`start`/`end`: unix ms | null; `state`:
  `"idle" | "active" | "ended"`). Реализация: новый метод `StatsDb.querySolarWindow(day, nowMs)`
  — берёт минутки дня (`pvPower_avg`), гонит через `computeSolarWindow` (для сегодня — с `nowMs`,
  для прошедших дней — без). За той же сессионной авторизацией, что остальной `/api/stats/*`.
- **`GET /api/stats/daily`** — два новых поля приедут автоматически (роут отдаёт строки `daily`).

## UI (`web/`)

- **Дашборд** (`app/(app)/page.tsx`): маленькая панель «Солнце сегодня» —
  `начало → конец` в локальном `HH:MM`, три состояния (idle → «не началось»,
  active → «идёт с HH:MM», ended → `HH:MM–HH:MM`). Клиент дергает `/api/stats/solar-window`
  на маунте и раз в 60 с (минутного разрешения достаточно).
- **`/stats`** (`app/(app)/stats/page.tsx`): в суточную таблицу — 2 колонки
  «Начало» / «Конец» (`HH:MM` или «—», если null). `DailyRow` (в `web/lib/stats.ts`)
  получает `solar_start_ts`/`solar_end_ts`; там же тип ответа `SolarWindow` + `fetchSolarWindow`.
- **Удаление старых событий**: убрать из фильтра журнала и из `evText`/меток
  `solar-charge-start`/`solar-charge-stop`; соответствующие i18n-ключи.
- **i18n** (`web/lib/i18n/dict.ts`, UA/RU/EN): ключи для заголовка панели, «начало»,
  «конец», «не началось», «идёт с …».

## Бэкенд: удаление дребезга

`server/src/stats/recorder.ts`:

- удалить блок гистерезиса Шмитта по `pvChargingPower` (константы `SOLAR_CHARGE_START_W`/

  и её сброс в `deriveEvents`).
- Recorder больше не выводит solar-события; окно считается не из диффа снапшотов, а
  ретроспективно из `samples_minute` в `db.ts`. Это осознанный перенос ответственности:
  дребезг событий заменяется одним расчётом по минуткам.

## Развязка модулей

- `stats/solar.ts` — чистая логика (функция + типы `SolarWindow`, `SolarState`), ноль
  зависимостей от БД/сети/времени. Потребители: `db.ts` (rollup, бэкофилл, `querySolarWindow`),
  роут в `server.ts`, UI (через API).
- `db.ts` — единственное место со схемой и SQL; знает про окно только через вызов
  `computeSolarWindow` над выбранными минутками.

## Развёртывание

- Миграция `v1→v2` (ALTER + бэкофилл) отрабатывает автоматически при первом старте нового
  билда. На Pi таблица `daily` уже с данными — `ALTER TABLE ADD COLUMN` безопасен,
  бэкофилл пересчитает историю из `samples_minute` (2 года).
- `deploy.sh` каталог `data/` не трогает — БД мигрирует на месте.
- Env-дефолты (200 Вт / 15 мин) достаточны; `server/.env` на Pi править не нужно, если
  дефолты устраивают (deploy.sh `.env` не перезаписывает).

## Явно вне рамок (YAGNI)

- Не удаляем исторические строки `solar-charge-*` из таблицы `events`.
- Не вводим настройку порога/устойчивости через UI (только env).
- Не считаем «пик мощности», «длительность окна» и прочую производную статистику —
  только две отметки времени.
