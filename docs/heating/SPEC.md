## 1. Цель

Сейчас управление отоплением реализовано на базе компонентов Tuya Smart WiFi:

- 3 WiFi-датчика температуры/влажности на батарейках;
- к котлу подключено WiFi смарт-реле с сухим контактом — при включении замыкает
  управляющие контакты котла и включает отопление, если температура на одном из
  датчиков падает ниже заданного значения;
- отдельный **насос контура тёплого пола** на своём смарт-реле, коммутирующем его
  питание **220 В**. Включается вместе с отоплением, выключается **с задержкой
  15 минут** после (выбег).

Важная деталь про насос: он обслуживает **только контур тёплого пола**. Всю
остальную систему прокачивает собственный насос котла. Если насос тёплого пола не
работает — батареи продолжают греть, вода в трубах не останавливается, и никакой
опасности для котла нет. Это определяет всё поведение при отказах (§6).

Цель — **уйти от облака Tuya**: свои датчики и реле на базе ESP32, вся логика
внутри дома.

## 3. Принятые решения

| Развилка | Решение |
|---|---|
| Где «мозг» термостата | На Raspberry Pi, свой Node-сервис |
| Поведение при потере связи с Pi | Реле само становится термостатом (лестница деградации, §6) |
| Питание датчиков | Все от сети (USB), постоянный WiFi, без deep sleep |
| Прошивки | **ESPHome** (Home Assistant не нужен, MQTT нативно) |
| Отношение к остальной системе | Модуль монолита sweethome: общий процесс, общий веб, общая авторизация, общий деплой |
| Алгоритм | Один **главный** датчик решает, остальные — мониторинг. Главный переключается из интерфейса |
| Насос | **Своя нода** со своим реле: он далеко от котла. Выбег 15 мин в прошивке, состояние котла берёт из MQTT (§6) |
| Ручное управление | Кнопка без фиксации и светодиод на **каждой** коробке, как у Tuya. Переключение держится, пока автомат не передумает (§6) |
| Датчики на ноде котла | Четыре `DS18B20`: подача, обратка, котельная, улица. Улица — на **отдельной** шине 1-Wire |
| Скоуп v1 | Термостат + история/графики + уведомления в Telegram |
| Авторизация | Общая auth-middleware хоста sweethome; `forward_auth` не нужен |
| Телеметрия котла | Только накладные `DS18B20` на подаче и обратке, в v1 **обязательны**. Опрос котла по родному протоколу (Optolink) **не делаем вообще** — тема закрыта |

## 4. Топология

```
┌─ Датчик «Гостиная»  ESP32-C3 + SHT41 ──┐
├─ Датчик «Спальня»   ESP32-C3 + SHT41 ──┤   WiFi
├─ Датчик «Детская»   ESP32-C3 + SHT41 ──┤  ──MQTT──▶ ┌──────────────┐
│                                        │            │  Mosquitto   │
├─ Нода котла   ESP32-WROOM ─────────────┤            │    на Pi     │
│    ├─ реле → сухой контакт Vitopend    │◀───────────┤              │
│    ├─ DS18B20 ×3: подача, обратка,     │            └──────┬───────┘
│    │              котельная  (шина 1)  │                   │
│    └─ DS18B20 улица          (шина 2)  │                   │
│                                        │          ┌──────────────────┐
└─ Нода насоса  ESP32-WROOM ─────────────┘          │ модуль heating   │
     └─ реле → 220 В на насос                       │ в sweethome      │
        (выбег 15 мин, состояние котла              │ (Node, :3000),   │
         слушает в MQTT напрямую)                   │ SQLite, Telegram │
                                                     └────────┬─────────┘
                                                              │
                                           веб-раздел /heating единого интерфейса
```

Ключевой принцип: **ноды подписаны на данные напрямую, а не только на команды
сервиса.** Нода котла слушает температуры всех трёх комнат и потому в любой момент
знает, тепло ли в доме. Нода насоса слушает состояние котла и потому знает, надо ли
крутить. Сервис нужен обоим для уставки, истории и удобств — но не для выживания.

Пять нод вместо четырёх — плата за то, что насос физически далеко от котла. Взамен
между ними появился брокер, то есть новая точка отказа; как она обходится, описано
в §6.

## 5. Контракт MQTT

Префикс — `heating/`. Датчики и реле публикуют средствами штатного MQTT-клиента
ESPHome; `status` — это Last Will (retained).

**Датчики** (`<room>` ∈ `livingroom` / `bedroom` / `kids`):

| Топик | Retain | Содержимое |
|---|---|---|
| `heating/<room>/sensor/temperature/state` | да | °C |
| `heating/<room>/sensor/humidity/state` | да | % |
| `heating/<room>/sensor/wifi_signal/state` | да | dBm |
| `heating/<room>/status` | да | `online` / `offline` (LWT) |

**Нода котла** (публикует):

| Топик | Retain | Содержимое |
|---|---|---|
| `heating/boiler/status` | да | `online` / `offline` (LWT) |
| `heating/boiler/switch/heat/state` | да | `ON` / `OFF` — фактическое состояние сухого контакта, по изменению |
| `heating/boiler/sensor/heat/state` | да | `0` / `1` — то же состояние, но **каждые 10 с**; это и значение, и признак жизни для ноды насоса |
| `heating/boiler/sensor/boilerroom_temperature/state` | да | °C, котельная (для L3) |
| `heating/boiler/sensor/outdoor_temperature/state` | да | °C, улица |
| `heating/boiler/sensor/flow_temperature/state` | да | °C, подача |
| `heating/boiler/sensor/return_temperature/state` | да | °C, обратка |
| `heating/boiler/sensor/level/state` | да | `0`…`3` — текущий уровень лестницы числом |

**Нода котла** (подписана):

| Топик | Retain | Содержимое |
|---|---|---|
| `heating/cmd/heat` | **нет** | `ON` / `OFF` — команда сервиса |
| `heating/cfg/setpoint` | да | °C, рабочая уставка |
| `heating/cfg/main_sensor` | да | имя главного датчика (`livingroom` / …) |
| `heating/cfg/hysteresis` | да | °C |
| `heating/<room>/sensor/temperature/state` | да | температуры всех трёх комнат |

**Нода насоса** (публикует):

| Топик | Retain | Содержимое |
|---|---|---|
| `heating/pump/status` | да | `online` / `offline` (LWT) |
| `heating/pump/switch/pump/state` | да | `ON` / `OFF` — фактическое состояние реле |
| `heating/pump/sensor/overrun_left/state` | да | сек до выключения, `0` если выбег не идёт |
| `heating/pump/sensor/level/state` | да | `0` / `1` — уровень P0 или P1 |

**Нода насоса** (подписана):

| Топик | Retain | Содержимое |
|---|---|---|
| `heating/boiler/sensor/heat/state` | да | `0` / `1` — состояние котла, приходит каждые 10 с |
| `heating/cfg/pump_overrun` | да | сек, длительность выбега (по умолчанию 900) |
| `heating/cfg/pump_antiseize` | да | сек простоя до летнего прогона (`0` — не гонять) |

Кнопка на коробке **не добавляет ни одного топика**. Флаг живёт внутри ноды, а
сервис узнаёт о нажатии сам: его команда расходится с фактическим состоянием реле,
которое нода и так публикует. Меньше контракта — меньше того, что может разъехаться.

Обрати внимание: нода насоса **не подписана ни на одну команду сервиса**. Она
зависит только от ноды котла и от конфигурации. Сервис не может ни включить, ни
выключить насос — и это правильно: у насоса нет ни одного сценария, где решение
человека было бы лучше правила «крутиться, пока котёл греет».

Два решения, которые стоит зафиксировать явно:

- **Команда и heartbeat — это одно и то же сообщение.** Сервис публикует
  `heating/cmd/heat` **каждый тик, то есть раз в 10 секунд**, независимо от того,
  менялось решение или нет. Отдельного heartbeat нет: свежесть команды и есть
  признак живого сервиса. Топик **не retained** — иначе нода приняла бы за свежую
  команду сообщение, оставшееся от умершего сервиса.

  Это сознательный отказ от событийной модели, по которой работает Tuya. Там реле
  ничего не решает само и просто держит последнее состояние, поэтому команда нужна
  только по событию. Наша нода обязана понять, когда брать управление на себя, а при
  событийной модели «сервис молчит, потому что не надо греть» и «сервис умер»
  неразличимы. Периодическая команда решает это без отдельного топика.

  Второе следствие того же выбора: сверка **самолечится**. Потерянное сообщение,
  пропущенная при перезагрузке команда, реле в неожиданном состоянии — всё это
  исправляется за десять секунд, тогда как событийная модель жила бы с расхождением
  до следующей смены решения. Платой стали шесть строк в прошивке, которые не дают
  сверке затирать нажатие кнопки (§6).
- **Кто главный датчик — знает нода, а не только сервис.** Она подписана на все
  три температуры и на retained `heating/cfg/main_sensor`, поэтому смена главного
  датчика из интерфейса не требует перепрошивки, а L1 работает при мёртвом
  сервисе. `setpoint`, `main_sensor` и `hysteresis` нода кэширует во флеш
  (`restore_value: true`): при старте берёт retained-значения из брокера, а если
  брокера нет — из флеша.

Отдельной «аварийной уставки» нет намеренно: на уровне L1 нода греет по той же
уставке и тому же датчику, что и сервис. Меняется только то, **кто** принимает
решение, а не то, каким оно будет.

Уровень едет **числом `0`…`3`**, а не строкой `L0`…`L3`: числовой канал уже
разбирается общим парсером сенсоров, и отдельный текстовый ради одного значения
не нужен. В человеческий вид уровень превращается в интерфейсе (§11) и в
уведомлениях (§13).

## 6. Лестница деградации и защита горелки

Каждый уровень включается, только когда верхний признан мёртвым.

| | Условие | Поведение реле |
|---|---|---|
| **L0** Норма | команда `heating/cmd/heat` приходит не реже 10 с | исполняет команду сервиса |
| **L1** Сервис умер | нет команды 5 мин, MQTT жив | сам термостат по главному датчику, уставка и гистерезис из кэша |
| **L2** Брокер умер | нет свежей комнатной температуры 30 мин | слепой цикл: 15 мин греет, 45 мин отдыхает |
| **L3** Страховка | **всегда поверх L0–L2** | котельная < 8 °C → греть; котельная > 45 °C → разомкнуть |

L3 — защита от абсурда: снизу от реальной угрозы разморозки, сверху от залипшего
контакта или ушедшей в разнос логики. Он **зашит в прошивку и не настраивается из
интерфейса** намеренно: его нельзя сломать через веб.

Верхний порог — именно 45 °C, а не 35. В котельной с работающим атмосферным котлом
30–35 °C — совершенно рабочая температура, и порог 35 °C регулярно глушил бы
отопление в мороз, то есть ровно тогда, когда оно нужнее всего. 45 °C в жилом доме
означает уже настоящую неисправность.

Нижний порог 8 °C **надо откалибровать на фазе 1**: если котельная не отапливается
и в мороз штатно уходит ниже 8 °C, L3 будет постоянно требовать грева и перебивать
нормальную логику. Реальные данные по котельной появятся сразу, как только нода
котла встанет на место, — тогда и уточним.

**Защита горелки действует на всех уровнях:** гистерезис 0.5 °C и минимум 5 минут
в каждом состоянии. Vitopend 100 — атмосферный котёл без модуляции, тактование
ему вредно.

**Значения по умолчанию** (всё, кроме L3, настраивается из веба):

| Параметр | Значение |
|---|---|
| Гистерезис | 0.5 °C |
| Период команды/heartbeat | 30 с |
| Порог L1 (нет команды) | 5 мин |
| Порог L2 (нет температуры) | 30 мин |
| Цикл L2 | 15 мин греет / 45 мин пауза |
| Антизаморозка L3 (котельная) | 8 °C, уточнить на фазе 1 |
| Перегрев L3 (котельная) | 45 °C |
| Минимальное время в состоянии | 5 мин |
| Выбег насоса | 15 мин (900 с) |
| Летний прогон насоса | 3 мин раз в 7 суток простоя |

### Кнопка на коробке

На каждой коробке — **кнопка без фиксации и светодиод**, как на Tuya-реле.
Нажатие переключает реле, светодиод показывает его состояние. Всё.

Одна тонкость, из-за которой это не совсем тривиально. У Tuya автоматика
**событийная**: облако шлёт команду, только когда температура пересекла порог,
поэтому реле держит то, что ему сказали последним — хоть кнопкой. У нас автомат
**сверяющий**: он каждые 10 секунд заново вычисляет нужное состояние. Простое
переключение реле он отменил бы через секунду.

Поэтому нажатие поднимает внутренний флаг, и правило снятия флага ровно одно:

> **Переключённое кнопкой состояние держится, пока автоматика не поменяет своё
> решение.** Как только автомат решил иначе, чем в момент нажатия, — флаг снимается,
> и дальше всё как обычно.

Это в точности повторяет поведение, к которому привык дом: нажал — сработало и
держится; сработала автоматика — она и рулит. Ни таймаутов, ни долгих нажатий, ни
отдельного «режима» в интерфейсе.

**L3 остаётся выше кнопки.** Страховка по котельной отменяет и её тоже: замкнутое
кнопкой реле при 45 °C в котельной разомкнётся. Это единственное исключение, и оно
не обсуждается.

**После перезагрузки флаг сбрасывается** — состояние определяет автомат.

**Чего кнопка не отменяет: защиту горелки.** Пять минут между переключениями
действуют и здесь. При монтаже это раздражает, но альтернатива — дать возможность
нащёлкать котлу тактование руками.

Один сценарий стоит знать. Если принудительно включить котёл летом, когда автомат
стабильно говорит «не грей», его решение не поменяется никогда, и котёл будет греть
до следующего нажатия. Ровно так же ведёт себя нынешнее Tuya-реле. Таймаут я
добавлять не стал — вместо этого сервис независимо следит за расхождением своей
команды с фактическим состоянием реле и через полчаса присылает напоминание (§13).
Кнопка при этом остаётся тупой кнопкой.


### Насос тёплого пола

Насос обслуживает **только контур тёплого пола**; остальную систему прокачивает
собственный насос котла. Из этого следует главное: **неработающий насос — это не
авария, а неудобство.** Батареи греют по-прежнему, вода в трубах движется, котлу
ничего не грозит. Холоднее становится только в комнатах с тёплым полом.

Насос стоит далеко от котла, поэтому у него **своя нода со своим реле**. Логика
целиком в прошивке, но между насосом и котлом теперь стоит брокер.

Правило нормальной работы:

- котёл включился → насос включается **в тот же момент**;
- котёл выключился → насос работает **ещё 15 минут**, затем гаснет;
- котёл включился во время выбега → таймер выбега сбрасывается.

Выбег нужен не котлу, а полу: в трубах у гребёнки остаётся горячая вода, и ещё
пятнадцать минут циркуляции размазывают это тепло по стяжке вместо того, чтобы
оставить его лежать одним пятном. Насос **не подчиняется** ни минимальному времени
в состоянии, ни гистерезису — это защита горелки, к нему она отношения не имеет.

**Откуда нода насоса знает про котёл.** Нода котла публикует своё состояние в
`heating/boiler/sensor/heat/state` числом `0`/`1` **каждые 10 секунд**, а не только
при изменении. Retained-топика `switch/heat/state` тут мало: он обновляется по
событию, и через час без переключений насос не отличил бы «котёл давно стоит» от
«котёл давно недоступен». Регулярная публикация даёт и значение, и свежесть.

**Своя лестница из двух уровней:**

| | Условие | Поведение насоса |
|---|---|---|
| **P0** Норма | состояние котла свежее, моложе 60 с | по правилу выше: вместе с котлом плюс выбег |
| **P1** Ослеп | состояния котла нет дольше 60 с | **насос выключается** |

Выключается — потому что работающий вслепую насос не даёт ничего. Он не спасает
котёл (тот прокачивается сам) и не греет пол (без горящего котла в контуре нет
тепла). Остаётся только счётчик: около 1.2 кВт·ч в сутки за красивую идею. Поэтому
при потере связи насос честно останавливается, и полы остывают ровно до тех пор,
пока связь не вернётся.

Свежесть состояния нужна именно для этого. Без неё нода не отличила бы «котёл не
горит» от «котёл недоступен», и залипший retained-`1` крутил бы насос вечно после
смерти ноды котла.

Ради полноты: сценарий «котёл греет, а насос стоит» существует и попадает в
уведомления — но это сообщение о неудобстве, а не о неисправности. Опасного
варианта «топим в неподвижную воду» здесь нет и быть не может.

**После перезагрузки ноды** реле поднимается разомкнутым и остаётся таким, пока не
придёт состояние котла — обычно это первые же десять секунд. Специального
безусловного прогона на старте не делаем: он имел бы смысл, если бы от насоса
зависела безопасность котла, а она не зависит.

**Летний простой.** Если насос не включался 7 суток, нода гоняет его 3 минуты.
Заклинивший после лета циркуляционный насос — классика, и лечится это пятью
строками в автомате. Работает только на уровне P0. Выключается из веба через
retained-топик `heating/cfg/pump_antiseize` (`0` — не гонять).


## 7. Железо

Нод пять: три комнатных датчика, нода котла и **отдельная нода насоса**. Насос
стоит далеко от котла, тянуть к нему провод через дом неудобно — проще поставить
рядом с ним свой контроллер. Цена этого решения не в железе, а в связи: между
котлом и насосом теперь стоит брокер, и §6 описывает, что с этим делать.

### Датчики, 3 шт

Плата — `ESP32-C3 SuperMini` (USB-C, размером с монету, дешёвая). У части ревизий
слабая антенна, но датчик не критичный узел, а `RSSI` будет виден в интерфейсе.
Сенсор — `SHT41` (±0.2 °C, ±1.8 %RH, I²C, компонент `sht4x`); годится и `SHT31`.
`BME280` не брать: ±1 °C по температуре для уставки слишком грубо.

**Сенсор обязательно вынести от платы на шлейфе 5–10 см.** ESP32 с постоянным
WiFi греется и завышает показания на 1–3 °C — это самая частая ошибка в
самоделках. Корпус — со щелями снизу и сверху, чтобы воздух проходил сам.

| Сигнал | Пин ESP32-C3 | Куда идёт |
|---|---|---|
| I²C SDA | `GPIO5` | `SDA` на плате SHT41 |
| I²C SCL | `GPIO6` | `SCL` на плате SHT41 |
| Питание | `3V3` | `VIN` SHT41 |
| Земля | `GND` | `GND` SHT41 |

`GPIO5` и `GPIO6` выбраны вместо «дефолтных» для C3 `GPIO8`/`GPIO9` намеренно.
На ESP32-C3 обе эти ноги — **strapping-пины**, их уровень в момент сброса задаёт
режим загрузки. С подтяжками I²C они уходят в высокое состояние, что как раз и
означает нормальную загрузку, поэтому обычно всё работает. Но любое устройство,
удерживающее шину в нуле в момент сброса, оставит ноду в режиме прошивки до
передёргивания питания. `GPIO5`/`GPIO6` — обычные ноги без побочных смыслов, и
этот класс проблем исчезает бесплатно.

Подтягивающие резисторы на шине I²C уже стоят на большинстве breakout-плат SHT41 —
свои добавлять не нужно. Все четыре провода идут одним шлейфом длиной 5–10 см:
это тот самый вынос сенсора от греющейся платы.

**Питание — сетевой адаптер 5 В / 1 А со штекером `5.5×2.5`**, гнездо ставится в
корпус датчика, от гнезда два провода паяются на пятачки `5V` и `GND` платы.

Так надёжнее, чем питать через USB-C: на дешёвых `SuperMini` этот разъём держится на
пятачках припоя и отрывается вместе с дорожками, если дёрнуть кабель. Питая плату
напрямую, мы выводим его из игры — он остаётся только для первой прошивки. Паяльник
всё равно в руках: шлейф сенсора паяется тем же заходом.

Три вещи, на которых тут спотыкаются:

- **Гнездо брать `5.5×2.5`, а не привычное `5.5×2.1`.** У штекера 2.5 мм внутреннее
  отверстие; на гнезде с центральным штырьком 2.1 мм он будет болтаться и давать
  пропадающий контакт. Диаметры должны совпасть.
- **Полярность — плюс в центре.** У этого адаптера так и есть, но проверить перед
  первым включением обязательно: обратная полярность на пятачке `5V` почти наверняка
  убьёт плату, защиты там нет.
- **Не держать одновременно адаптер и USB.** При первой прошивке или при отладке
  адаптер отключать: иначе получим встречное питание через `VBUS`.

**`HLK-5M05` внутрь датчиков не ставим**,
хотя в силовые коробки поставили, и причины тут три.

Главная — тепловая, и она специфична для этого проекта. Весь дизайн датчика построен
вокруг борьбы с собственным нагревом: сенсор на шлейфе 5–10 см, корпус со щелями,
всё ради того, чтобы не завысить показания на пару градусов. `HLK-5M05` при КПД
около 70 % рассеивает внутри корпуса примерно столько же тепла, сколько сам ESP32,
то есть удваивает то, с чем мы боремся. Ставить источник тепла в термометр — плохая
идея независимо от того, насколько аккуратно он собран.

Вторая: это три коробки с сетевым напряжением в гостиной, спальне и **детской**.
Котельная — техническое помещение, там самоделка с 220 В уместна. Жилые комнаты —
нет, тем более что USB-зарядка это сертифицированное изделие, а наша коробка нет.

Третья: сеть в стене привязывает датчик к месту и превращает установку в
электромонтаж. Зарядку можно переткнуть в другую розетку, если выяснится, что
датчик висит неудачно, — а на фазе 1 мы как раз будем смотреть, где он врёт.

Если у какой-то точки не окажется розетки поблизости, правильное решение — тянуть
туда **5 В от зарядки**, а не 220 В. Тонкий безопасный провод вместо силового.

### Нода котла

`ESP32-DevKitC` на `WROOM-32`: компактность не нужна, нужна проверенная антенна и
запас ног. Реле — **одноканальное, электромеханическое**, с оптронной развязкой,
контакты `NO`/`COM`/`NC` на 250 VAC / 10 A. Твердотельное не годится: на клеммах
котла заранее неизвестны ни род тока, ни полярность.

| Сигнал | Пин ESP32 | Куда идёт |
|---|---|---|
| Реле котла | `GPIO16` | `IN` релейного модуля |
| Кнопка | `GPIO27` | Кнопка на корпусе, второй контакт на `GND` |
| Светодиод | `GPIO26` | Светодиод в кнопке, через резистор на `GND` |
| Шина 1-Wire №1 | `GPIO4` | Три `DS18B20`: подача, обратка, котельная |
| Шина 1-Wire №2 | `GPIO17` | `DS18B20` **уличный** |
| Питание обмотки | `5V` (`VIN`) | `JD-VCC` релейного модуля |
| Питание логики реле | `3V3` | `VCC` релейного модуля (перемычка снята) |
| Питание датчиков | `3V3` | `VDD` всех четырёх `DS18B20` |
| Земля | `GND` | общая: модуль реле, обе шины 1-Wire |

На каждой шине 1-Wire свой резистор 4.7 кОм между линией данных и `3V3`, оба —
**у платы**, а не у датчика.

**Что меряем и зачем:**

| Датчик | Шина | Зачем |
|---|---|---|
| Подача | 1 | Факт работы горелки: замкнули контакт — подача обязана расти |
| Обратка | 1 | Вместе с подачей даёт дельту, то есть признак живой циркуляции |
| Котельная | 1 | Единственный вход уровня L3 (§6) |
| Улица | 2 | Мониторинг; в перспективе — погодозависимое регулирование (§19) |

**Подача и обратка ставятся накладно**, в клипсе на трубу и обязательно **под
утеплитель поверх датчика**: голый датчик на трубе меряет наполовину воздух
котельной. Даже так это температура стенки трубы, а не воды — обычно на 2–5 °C
ниже и с задержкой в пару минут. Для абсолютных значений так себе, для ответа
«горит или нет» и для дельты — более чем достаточно, а больше нам от них и не надо.

**Про котельную.** Она маленькая, полуподвальная, без радиаторов, и греется только
от самого котла и труб. Это делает её показания зависимыми от работы котла, что для
L3 как раз нормально: страховка и должна срабатывать по тому, что происходит рядом с
котлом. Но нижний порог 8 °C придётся калибровать по факту — помещение без
отопления зимой может уходить ниже, и тогда L3 начнёт требовать грева на ровном
месте. Данные появятся сразу после установки (§20).

**Уличный датчик сидит на отдельной шине намеренно.** Его кабель идёт наружу, где
влага, ультрафиолет и механика, и рано или поздно он получит обрыв или замыкание.
На общей шине это уронило бы вместе с ним датчик котельной — а от него зависит
уровень L3, последняя страховка всей системы. Отдельная шина стоит одну свободную
ногу и один резистор, и полностью развязывает эти отказы.

Кабель на улицу — витая пара или экранированный, до ~20 м работает без ухищрений.
Сам датчик — в тени, лучше на северной стене, под козырьком, подальше от окон,
вытяжек и кондиционеров: иначе он будет мерить не улицу, а то, что дом из себя
выдыхает.

### Нода насоса

`ESP32-DevKitC` на `WROOM-32` — та же плата, что у котла. Решено так: связь в том
районе дома не блестящая, а `C3 SuperMini` с его известными проблемами антенны
добавил бы отвалов на ровном месте. Разница в сотню гривен того не стоит, к тому же
одинаковые платы — это один набор граблей на две ноды вместо двух.

Реле — **одноканальное**, те же требования, коммутирует фазу питания насоса 220 В.

| Сигнал | Пин ESP32 | Куда идёт |
|---|---|---|
| Реле насоса | `GPIO16` | `IN` релейного модуля |
| Кнопка | `GPIO27` | Кнопка на корпусе, второй контакт на `GND` |
| Светодиод | `GPIO26` | Светодиод в кнопке, через резистор на `GND` |
| Питание обмотки | `5V` (`VIN`) | `JD-VCC` релейного модуля |
| Питание логики реле | `3V3` | `VCC` релейного модуля (перемычка снята) |
| Земля | `GND` | общая |

### Требования к релейным модулям

Нужны **два одноканальных** модуля, а не один двухканальный: ноды теперь разные.

| Требование | Почему |
|---|---|
| Обмотка на **5 В** | В коробке есть 5 В и нет 12 В; заводить третье напряжение ради реле незачем |
| **Оптронная развязка** входа | Иначе бросок от обмотки прилетает в ESP32 |
| Отдельная перемычка **`VCC` / `JD-VCC`** | Ключевой пункт, см. ниже |
| Контакты `NO`/`COM`/`NC`, **250 VAC / 10 A** | Насос и, возможно, сетевая цепь термостата |

Про перемычку стоит сказать отдельно, потому что на ней спотыкаются все. У типового
модуля `VCC` (питание оптрона) и `JD-VCC` (питание обмотки) соединены перемычкой, и
тогда модуль хочет 5 В на входе — а ESP32 выдаёт 3.3 В, чего оптрону может не
хватить. Правильное подключение: **перемычку снять**, на `JD-VCC` подать 5 В для
обмотки, на `VCC` — 3.3 В с платы, землю общую. Тогда вход `IN` работает от 3.3 В
логики надёжно. Модули **на 12 В брать нельзя**: такого напряжения у нас нет.

Входы `IN` у подавляющего большинства модулей **активны низким уровнем** — реле
замыкается, когда на входе ноль. Это учтено в прошивке (`inverted: true` у пина),
но проверяется тестером на контактах при сборке, а не по светодиоду модуля: у многих
плат светодиод горит как раз в разомкнутом состоянии.

**Тот же модуль годится и для сухого контакта котла.** «Сухой контакт» — это ровно
то, что даёт электромеханическое реле: `COM`–`NO` суть два куска металла,
гальванически развязанные и от обмотки, и от контроллера. Паспортные 250 VAC / 10 A
— потолок, а не требование, слаботочку через них коммутировать можно.

Оговорка касается долгого срока, и документация её подтвердила. Силовые реле с
контактами `AgNi`/`AgCdO` рассчитаны на заметный ток: он выжигает окисную плёнку при
каждом переключении. У Vitopend цепь термостата — **24 В и порядка 10 мА**, при таких
величинах выгорать плёнке нечем, и через год-другой возможен неустойчивый контакт.
Это классическая проблема под названием «dry circuit», и правильная деталь против
неё — реле с **золочёными контактами**, они как раз для сигнальных цепей.

Тем не менее берём обычные модули, и вот почему.

Во-первых, прямо сейчас эту же цепь коммутирует Tuya-реле, внутри которого стоит
такой же копеечный электромеханический модуль — то есть эмпирически нагрузка обычным
реле переключается, и не первый год.

Во-вторых и главное: **этот отказ мы теперь замечаем сразу.** Датчик подачи даёт
тревогу `not-firing` — контакт замкнут пятнадцать минут, а подача не нагревается.
Именно так выглядит окислившийся контакт со стороны системы. То есть вместо того
чтобы платить за золочёные контакты в надежде избежать проблемы, мы просто
обнаружим её в тот же час, когда она появится, и заменим модуль за 38 ₴.

Твердотельная альтернатива тут не годится: 10 мА ниже тока удержания симистора,
а полярность постоянного тока (если он постоянный) заранее неизвестна.

Оба реле включены нормально разомкнутыми (`COM`–`NO`): обесточенная нода не греет
и не крутит насос. При полном отказе питания и котёл, и насос должны остановиться,
а не остаться включёнными.

**В первые доли секунды после подачи питания** пины ESP32 в неопределённом
состоянии, и модуль с активным низким уровнем может коротко щёлкнуть. Котлу и
насосу такой щелчок безразличен, но если хочется чисто — подтяжка 10 кОм на `3V3`
на входе `IN`.

**Кнопка и светодиод — на обеих нодах одинаково.** Кнопка **без фиксации**, замыкает
`GPIO27` на землю; подтяжка внутренняя, внешних деталей не надо. Светодиод просто
повторяет состояние реле: горит — замкнуто. Удобнее брать встроенный в саму кнопку —
тогда в корпусе одно отверстие вместо двух. Если светодиод в кнопке без резистора,
поставить последовательно 220–330 Ом.

Онбордовый светодиод платы для этого не годится: он окажется внутри закрытой
коробки, где его никто не увидит. Кнопка панельная и **влагозащищённая в обеих
коробках** — они обе `IP54`, и дырка под обычную кнопку сводит эту защиту на нет.

Брать надо именно **без фиксации** (momentary, «звонковую»): кнопка с фиксацией
механически запомнит своё положение, а прошивка про это ничего не знает — после
перезагрузки утопленная кнопка и состояние реле разъедутся, и понять по виду коробки,
что происходит, станет невозможно.

`GPIO26` и `GPIO27` выбраны как обычные ноги без побочных смыслов, в отличие от
`GPIO2`, куда обычно посажен онбордовый светодиод: `GPIO2` — strapping-пин.

Ещё две ноги, которые нельзя занимать под реле на классическом ESP32:
strapping-пины `GPIO0`, `GPIO2`, `GPIO5`, `GPIO12`, `GPIO15` — их уровень в момент
подачи питания меняет режим загрузки. `GPIO34`–`GPIO39` только на вход. Выбранные
`GPIO16`, `GPIO17` и `GPIO4` свободны от этих оговорок — но **только на `WROOM-32`**:
на модулях `WROVER` `GPIO16`/`GPIO17` заняты под PSRAM.

### Связь в котельной

Котельная — полуподвальное помещение, и теоретически это плохой расклад для WiFi:
ниже уровня земли, бетон, металл котла и труб вокруг. **На практике связь там
нормальная**: в котельной уже годами работают Tuya-реле с сухим контактом, малина и
смарт-счётчики. Это наблюдение весит больше любых рассуждений про затухание, так что
берём обычные `WROOM-32` и внешние антенны не закладываем.

Оставляем только дешёвую проверку: когда ноды будут собраны на столе, отнести их на
будущие места и посмотреть `RSSI` полчаса. Не гейт перед закупкой, а десять минут
здравого смысла. Если вдруг окажется ниже −80 dBm — существует `ESP32-WROOM-32U` с
разъёмом `IPEX` под внешнюю антенну, но рассчитывать на это не надо.

**Сетевого кабеля в котельную не протянуть — только беспроводное.** Это ограничение
дома, и оно закрывает вопрос об Ethernet как запасном канале для ноды котла: такого
варианта у нас нет в принципе. Если связь когда-нибудь испортится, лечить придётся
антенной или точкой доступа поближе, но не кабелем. На сигнальные провода внутри
дома ограничение не распространяется: кабель к уличному датчику протягивается без
проблем.

Чего делать **не** нужно ни при каком раскладе: пытаться лечить слабый сигнал
настройками ESPHome. `fast_connect` ускоряет подключение, но не улучшает приём, а
отключённый `reboot_timeout` у ноды котла (§8) означает, что от зависшего WiFi-стека
она сама не оправится — это сознательный размен ради работы без сети.


### Коробка насоса

**Схема ровно как у нынешнего Tuya-реле:** один корпус, в него заходит одна линия
220 В, она же питает контроллер и она же коммутируется реле на насос. Никаких
отдельных вводов, никакого второго питания.

```
одна линия 220 В ──┬──▶ HLK-5M05 ──▶ 5 В ──▶ контроллер
                   └──▶ COM реле ──NO──▶ насос
```

Ввод берём с той же линии, что сейчас питает Tuya-реле насоса. Она всегда под
напряжением — иначе контроллер терял бы питание вместе с выключенным насосом.

Предохранитель стоит **на вводе**, то есть защищает обе ветки сразу. Номинал
подбирается по мощности насоса (для типовых 30–100 Вт это 1–2 А), и для тонкой
ветки на `HLK-5M05` такого номинала более чем достаточно: провод 0.75 мм² держит
куда больше.

Отличие от Tuya только одно, зато существенное: там это сертифицированное залитое
изделие, а у нас самоделка. Поэтому дисциплина монтажа целиком на нас. Распаечная
коробка **IP54** с гермовводами:

- **предохранитель** на линии насоса (держатель 5×20 мм внутри коробки), номинал по
  мощности насоса;
- сетевая часть держится **своей стороны коробки**, слаботочка — своей, они не идут
  одним жгутом и не пересекаются над платой;
- клеммники **винтовые**, многожильный провод только в гильзах, ничего скрученного;
- питание ноды — модуль `HLK-5M05` (220→5 В, **5 Вт**, залитый, под пайку на плату)
  внутри той же коробки, а не USB-зарядка в удлинителе. Именно 5 Вт, а не
  распространённый `HLK-PM01`: у того 3 Вт, то есть 600 мА, а нам нужно покрыть пик
  Wi-Fi у `WROOM-32` (до ~500 мА) плюс обмотку реле — впритык и без запаса;
- сечение провода на насос — по его току, с запасом.

IP54 тут не догма — рядом с насосом просто бывает вода, а герметичная коробка стоит копейки. Если место сухое и защищённое, обычной закрытой коробки хватит.

```
        ┌──────────── коробка насоса, IP54 ────────────┐
 220 В  │  ╔═══════ СЕТЕВАЯ СТОРОНА ═══════╗           │
 ─ввод─▶│  ║ [предохр.] ─ L ─┬─ реле ──────╫──────────▶│─▶ насос (L)
        │  ║                 └─ HLK-5M05 ──╫──┐        │
        │  ║ N ──────────────┬─────────────╫──┤        │─▶ насос (N)
        │  ║ PE ─────────────┴─────────────╫──╫───────▶│─▶ насос (PE)
        │  ╚═══════════════════════════════╝  │ 5 В    │
        │  ╔═════ СЛАБОТОЧНАЯ ════════════╗   ▼        │
        │  ║  ESP32-DevKitC ── GPIO16 ── IN ─ реле     │
        │  ╚═══════════════════════════════════════╝   │
        └──────────────────────────────────────────────┘
```

| № | Откуда | Куда | Провод |
|---|---|---|---|
| 1 | Фаза ввода 220 В | Держатель предохранителя, вход | 1.5 мм² |
| 2 | Держатель предохранителя, выход | Клеммник `L` | 1.5 мм² |
| 3 | Клеммник `L` | `AC-L` на `HLK-5M05` | 0.75 мм² |
| 4 | Клеммник `L` | `COM` реле | 1.5 мм² |
| 5 | `NO` реле | Клеммник «насос L» | 1.5 мм² |
| 6 | Ноль ввода | Клеммник `N` | 1.5 мм² |
| 7 | Клеммник `N` | `AC-N` на `HLK-5M05` | 0.75 мм² |
| 8 | Клеммник `N` | Клеммник «насос N» | 1.5 мм² |
| 9 | `PE` ввода | Клеммник `PE` | 1.5 мм² |
| 10 | Клеммник `PE` | Корпус насоса | 1.5 мм² |
| 11 | `+5V` `HLK-5M05` | `VIN` ESP32 и `JD-VCC` релейного модуля | 0.5 мм² |
| 12 | `GND` `HLK-5M05` | `GND` ESP32 и `GND` релейного модуля | 0.5 мм² |
| 13 | `3V3` ESP32 | `VCC` релейного модуля (перемычка снята) | 0.5 мм² |
| 14 | `GPIO16` ESP32 | `IN` релейного модуля | 0.5 мм² |
| 15 | `GPIO27` и `GND` ESP32 | Кнопка на корпусе | 0.5 мм² |
| 16 | `GPIO26` через резистор 220 Ом и `GND` | Светодиод в кнопке | 0.5 мм² |

Гермовводов два: ввод 220 В и кабель насоса. Плюс отверстие под кнопку — она
влагозащищённая, иначе `IP54` теряет смысл.

**Питание есть на месте.** Врезаемся в ту же линию, которая сейчас питает Tuya-реле
насоса, — отдельную тянуть не нужно. Для ноды котла сеть в котельной тоже есть, так
что вариант с USB-зарядкой при слаботочных клеммах термостата реализуем.

Типовой циркуляционный насос тёплого пола потребляет 30–100 Вт, то есть меньше
0.5 А, и реле 10 A для него избыточно с большим запасом. **Мощность конкретного
насоса надо посмотреть на его шильдике** — если это вдруг что-то мощное, реле и
предохранитель придётся пересчитать.

Разница с щитком на DIN-рейке тут не в электрике, а в том, что аккуратность держится
целиком на монтажнике: в щитке компоновка навязана рейкой, в коробке её надо
продумать самому. Поэтому раскладку внутри стоит нарисовать до пайки, а не по ходу.

### Клеммы термостата на Vitopend: что говорит документация

Разобрано по трём документам Viessmann, и картина сходится.

**Где клеммы.** В [сервисной инструкции Vitopend 100 Typ WH1](https://www.kesselheld.de/content/uploads/2017/12/wartungsanleitung-viessmann-vitopend-100.pdf)
шаг ввода в эксплуатацию звучит так: «Brücke zwischen Klemmen X 4.1 und X 4.2
entfernen» — при подключении термостата снять **заводскую перемычку**. В
[монтажной инструкции родного термостата Uhrenthermostat-F](https://www.fliegervilla.at/app/download/5800464367/montage-f.pdf)
раздел «Anschluss an Vitopend 100» уточняет по исполнениям:

| Исполнение | Что снимать |
|---|---|
| `WH1`, `WHE` | Перемычку между `X3.1` и `X3.2` в разъёме `X3` |
| `WH0` | Перемычку между клеммами `1` и `L` — **буква `L` означает фазу** |

Нумерация в двух документах разная (`X 4.1/4.2` против `X3.1/3.2`) — видимо,
ревизии платы управления. Практический ориентир один: **искать разъём с заводской
перемычкой**, термостат ставится вместо неё.

**Что за цепь.** Ключ дала [планировочная документация Vitopend 100 WH1 / 200 WH2](https://www.intec-heizung.de/media/pdf/ed/36/31/Viessmann-Vitopend-100-WH1-Vitopend-200-WH2-Planungsanleitung.pdf).
Для термостата `Uhrenthermostat-A`, который питается от самого котла:

> Nennspannung: **24 V**
> Nennbelastbarkeit des potenzialfreien Kontaktes: **10 mA, 24 V~**

Косвенно то же подтверждает требование к проводке: «Die Leitung zum
Uhrenthermostat-F darf nicht unmittelbar mit 230/400 V-Leitungen zusammen verlegt
werden», кабель двухжильный 0.75 мм², максимум 30 м. Запрет прокладывать вместе с
силовыми линиями имеет смысл только для слаботочной цепи.

**Вывод: на клеммах беспотенциальный вход примерно 24 В и порядка 10 мА.** Значит:

- **коммутируемая цепь слаботочная** — реле нагружено пренебрежимо мало, и по
  контактам вопросов нет вовсе. Но питание самой ноды всё равно берётся от сети, так
  что коробка котла остаётся сетевой сборкой, просто с очень лёгкой нагрузкой;
- **10 мА при 24 В — ровно та зона, где силовое реле работает ненадёжно.** Порог,
  который я назвал наугад, документация подтвердила буквально. Подробности ниже.

**Проверить на месте всё равно надо** — исполнение `WH0` подключается к фазе, и
перепутать эти два случая было бы дорого. Достаточно посмотреть шильдик и померить
напряжение на разомкнутых клеммах: 24 В — работаем по слаботочному варианту, 230 В —
коробка становится такой же, как у насоса.

### Коробка котла

Собирается **по тому же образцу, что и коробка насоса**: сетевой ввод, `HLK-5M05`
внутри, предохранитель, разнос сетевой и слаботочной сторон. Разница только в том,
что реле здесь ничего не питает, а лишь замыкает беспотенциальные клеммы термостата.

Почему не USB-зарядка, хотя коммутируемая цепь слаботочная. Заманчиво было бы
оставить коробку вовсе без сети: тогда никакая неисправность не занесёт 230 В на
24-вольтовый вход платы управления котла, а это дорогая железка. Но зарядка в
розетке — это отдельный дешёвый блок питания в тёплом помещении, торчащий кабель и
розетка, которую однажды займут подо что-нибудь ещё. Как точка отказа она хуже
залитого модуля. К тому же прецедент рядом: нынешнее Tuya-реле у котла устроено
ровно так же — питается от сети и отдаёт сухой контакт из одного корпуса, и работает
не первый год. Одинаковые коробки вдобавок означают один набор граблей на две сборки
и один запасной `HLK` на всё.

Но одну вещь надо держать в голове при монтаже. В коробке насоса «жертвой» ошибки
будет сам насос, а здесь — плата управления котла, которая ждёт на своих клеммах
24 В. Поэтому провода к клеммнику термостата идут **строго по слаботочной стороне**,
своим жгутом, и рядом с сетевой частью не проходят нигде.

| № | Откуда | Куда | Провод |
|---|---|---|---|
| 1 | Фаза ввода 220 В | Держатель предохранителя, вход | 0.75 мм² |
| 2 | Держатель предохранителя, выход | `AC-L` на `HLK-5M05` | 0.75 мм² |
| 3 | Ноль ввода | `AC-N` на `HLK-5M05` | 0.75 мм² |
| 4 | `PE` ввода | Клеммник `PE` | 0.75 мм² |
| 5 | `+5V` `HLK-5M05` | `VIN` ESP32 и `JD-VCC` релейного модуля | 0.5 мм² |
| 6 | `GND` `HLK-5M05` | `GND` ESP32, реле, обеих шин 1-Wire | 0.5 мм² |
| 7 | `3V3` ESP32 | `VCC` реле (перемычка снята) | 0.5 мм² |
| 8 | `GPIO16` ESP32 | `IN` релейного модуля | 0.5 мм² |
| 8a | `GPIO27` и `GND` ESP32 | Кнопка на корпусе | 0.5 мм² |
| 8b | `GPIO26` через резистор 220 Ом и `GND` | Светодиод в кнопке | 0.5 мм² |
| 9 | `COM` и `NO` реле | Клеммник «термостат котла», два провода | 0.75 мм² |
| 10 | `GPIO4`, `3V3`, `GND` | Клеммник «1-Wire дом»: подача, обратка, котельная параллельно | 0.5 мм², экранированный |
| 11 | `GPIO17`, `3V3`, `GND` | Клеммник «1-Wire улица» | витая пара, экранированная |

У `HLK-5M05` выводы под пайку в плату, а не винтовые клеммы. В распаечной коробке
это значит: провода паяются прямо на выводы, места пайки закрываются термоусадкой, а
сам модуль сажается на площадку и фиксируется, чтобы не болтался на проводах. Своя
защита от КЗ и перегрузки у модуля есть, так что предохранитель на вводе нужен ради
проводки, а не ради него.

Предохранитель здесь маленький: нагрузка только `HLK-5M05`, то есть меньше 100 мА
по сети. Хватит 0.5 А. Сечение сетевого провода 0.75 мм² — по той же причине, тянуть
1.5 мм² не за чем.

Если на клеммах термостата вдруг окажется 230 В (исполнение `WH0`), меняется ровно
одно: цепь термостата переезжает на сетевую сторону коробки и получает провод
1.5 мм². Всё остальное — корпус, питание, предохранитель — уже готово.

## 8. Прошивки ESPHome

- Общий `sensor-common.yaml` подключается в три файла комнат через `packages:` —
  конфиг конкретного датчика вырождается в имя, MQTT-префикс и GPIO.
- Секреты (WiFi, MQTT, OTA, пароль API) — в `secrets.yaml`, мимо гита.
- Сборка: `docker run ghcr.io/esphome/esphome` на `piligrim2`. Первая заливка по
  USB, дальше только OTA. **На малине ESPHome не ставим** — 905 МБ ОЗУ для
  компиляции прошивок мало.
- Прошивок четыре: `sensor-common.yaml` с тремя обёртками комнат, `boiler-node.yaml`
  и `pump-node.yaml`.
- Лестница L0–L3 в ноде котла — явный конечный автомат на `lambda` внутри
  `interval: 10s`, порядка 70 строк. Штатный `climate: thermostat` не подходит:
  ему нужен один источник температуры, а у нас их три с приоритетом.
- Автомат ноды насоса заметно проще: два уровня, таймер выбега и таймер летнего
  прогона, порядка 30 строк в таком же `interval: 10s`.
- **Свежесть данных нода считает сама.** Сенсоры `mqtt_subscribe` отдают только
  значение, без метки времени, поэтому у каждого входа (`heat`, три температуры)
  в `on_value` запоминаем `millis()` в глобальную переменную. Вся лестница
  построена на «сколько прошло с последнего сообщения», так что без этих отметок
  она попросту не работает.
- Оба `switch: gpio` (`heat` у котла, `pump` у насоса) с `restore_mode: ALWAYS_OFF` —
  после перезагрузки контакты разомкнуты, автомат в течение секунд решает заново.
  Нода насоса на старте включает реле на 15 минут безусловно (§6).
- Нода котла публикует своё состояние **каждый тик**, а не только при изменении:
  на этом держится свежесть, по которой нода насоса отличает P0 от P1.
- **У реле-ноды отключаем штатный `reboot_timeout`** (`wifi:` и `mqtt:`). По
  умолчанию ESPHome перезагружает ноду, потерявшую связь на 15 минут, — а нам
  ровно в этот момент надо продолжать греть, а не ребутиться.

## 9. Модуль heating в sweethome

Пакеты `modules/heating` и `packages/heating-shared` в монорепо `sweethome`
(Node ≥ 24, TypeScript, jest); модуль реализует контракт `HomeModule`
(`@sweethome/shared/module`) — тот же, что и у инвертора.

**Ядро — чистая функция.** Всё решение термостата сводится к

```ts
decide(input: ThermostatInput, cfg: ThermostatConfig): Decision
```

На входе — температуры с метками времени, состояние реле, момент последнего
переключения и текущее время; на выходе — команда и причина. Никаких сайд-эффектов,
поэтому гистерезис, минимальное время в состоянии, устаревшие данные и пропавший
датчик покрываются тестами без брокера и железа.

**Модули:**

| Файл | Ответственность |
|---|---|
| `thermostat.ts` | чистое ядро `decide()` |
| `mqtt.ts` | подписки, LWT, публикация команд и конфигурации |
| `store.ts` | SQLite на `node:sqlite` |
| `notify.ts` | Telegram |
| `module.ts` + `router.ts` | сборка `HomeModule`: REST-роутер, WS-снапшоты, `start`/`stop` |
| `config.ts` | свои ключи в общем `server/.env` |

**Хранение** (`server/data/heating/heating.db`):

```sql
-- Сырые замеры, пишутся раз в 60 с по каждой живой ноде.
-- node — это id комнаты либо 'boilerroom' для датчика котельной.
CREATE TABLE samples (
  ts       INTEGER NOT NULL,   -- unix ms
  node     TEXT    NOT NULL,
  temp     REAL,               -- °C, NULL если значение не приходило
  humidity REAL,               -- %, NULL у DS18B20
  rssi     INTEGER,            -- dBm, NULL у проводных датчиков
  PRIMARY KEY (ts, node)
);

-- Часовые агрегаты. Заполняются при сворачивании сырых данных старше 30 дней.
CREATE TABLE samples_hourly (
  hour         INTEGER NOT NULL,  -- unix ms начала часа
  node         TEXT    NOT NULL,
  temp_avg     REAL,
  temp_min     REAL,
  temp_max     REAL,
  humidity_avg REAL,
  PRIMARY KEY (hour, node)
);

-- Событие пишется при изменении любого из состояний — не по таймеру.
CREATE TABLE boiler_events (
  ts         INTEGER PRIMARY KEY,  -- unix ms
  heat       INTEGER NOT NULL,     -- 0/1, состояние сухого контакта
  pump       INTEGER NOT NULL,     -- 0/1, состояние реле насоса
  level      TEXT    NOT NULL,     -- 'L0'…'L3', уровень ноды котла
  pump_level TEXT    NOT NULL,     -- 'P0'/'P1', уровень ноды насоса
  reason     TEXT    NOT NULL      -- человеческое объяснение от decide()
);

-- Настройки: ключ = поле Settings, значение = JSON.
CREATE TABLE settings (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

**Хранение и объём.** Сырые данные живут 30 дней, дальше сворачиваются в часовые
агрегаты и удаляются; сворачивание запускается раз в 6 часов. Пять источников
температуры (три комнаты, котельная, улица) × 1440 замеров в сутки — около 7.2
тысяч строк в день, порядка 220 тысяч за месяц хранения сырых, то есть единицы
мегабайт. Часовые агрегаты за год — меньше 40
тысяч строк. Для SD-карты малины это несущественная нагрузка. Подход и стиль —
как в `stats/db.ts` инвертора.

**Порча данных не должна ронять сервис.** Настройки читаются по одному полю: если
в базе окажется мусор, битое поле откатывается на значение по умолчанию, а
остальные применяются. Потерять уставку из-за одного испорченного ключа было бы
глупо.

**API** (под `/api/heating`, смонтирован хостом `sweethome` так же, как у инвертора).
Все ответы — JSON, все времена — unix ms, все температуры — °C числом с плавающей
точкой, `null` означает «данных нет» и никогда не подменяется нулём. Личность и
роль запроса приходят из системного `/api/me` — отдельного маршрута для этого
модулю не нужно.

| Метод | Путь | Назначение | Роль |
|---|---|---|---|
| `GET` | `/api/heating/state` | снапшот целиком | любая |
| `GET` | `/api/heating/settings` | текущие настройки | любая |
| `PUT` | `/api/heating/settings` | частичное изменение настроек | `admin` |
| `GET` | `/api/heating/history` | `?from&to[&node]` — серии для графиков | любая |
| `GET` | `/api/heating/stats/daily` | `?from&to` — минуты горения по дням | любая |
| `WS` | `/ws/heating` | push снапшота при каждом тике | любая |

`GET /api/heating/state` — снапшот:

```json
{
  "now": 1785400000000,
  "rooms": [
    {
      "room": "livingroom",
      "title": "Гостиная",
      "temp": 21.4,
      "humidity": 41.2,
      "rssi": -58,
      "online": true,
      "updatedAt": 1785399988000
    }
  ],
  "boiler": {
    "online": true,
    "heat": true,
    "level": "L0",
    "boilerRoomTemp": 17.5,
    "outdoorTemp": -4.2,
    "flowTemp": null,
    "returnTemp": null,
    "updatedAt": 1785399995000
  },
  "pump": {
    "online": true,
    "on": true,
    "overrunLeft": 0,
    "level": "P0",
    "updatedAt": 1785399996000
  },
  "settings": {
    "mainSensor": "livingroom",
    "setpoint": 21,
    "hysteresis": 0.5,
    "minStateSeconds": 300,
    "staleAfterSeconds": 1800,
    "pumpOverrunSeconds": 900,
    "pumpAntiseizeSeconds": 604800,
    "telegramEnabled": true
  },
  "desiredHeat": true,
  "reason": "20.6 °C ниже уставки 21 °C"
}
```

`desiredHeat` трёхзначен: `true`, `false` и **`null`** — последнее означает, что
сервис не в состоянии решать (нет свежих данных главного датчика) и намеренно
молчит в MQTT, роняя ноду на её собственную лестницу. `reason` в этот момент
объясняет почему и показывается в интерфейсе как есть.

`PUT /api/heating/settings` принимает **частичный** объект — только изменяемые
поля, остальные берутся из текущих:

```json
{ "setpoint": 22.5 }
```

Отвечает полным объектом настроек после применения. При недопустимом значении —
`400` и текст на русском, готовый к показу пользователю без переформулирования:

```json
{ "ok": false, "error": "Поле «уставка» вне допустимого диапазона 5…30" }
```

Допустимые значения:

| Поле | Диапазон | По умолчанию |
|---|---|---|
| `mainSensor` | один из `id` комнат | `livingroom` |
| `setpoint` | 5…30 | 21 |
| `hysteresis` | 0.1…3 | 0.5 |
| `minStateSeconds` | 60…3600 | 300 |
| `staleAfterSeconds` | 300…7200 | 1800 |
| `pumpOverrunSeconds` | 0…3600 | 900 |
| `pumpAntiseizeSeconds` | 3600…2592000 или `0` (выключить) | 604800 |
| `telegramEnabled` | `true` / `false` | `true` |

`GET /api/heating/history?from=…&to=…[&node=…]`:

```json
{
  "samples": [{ "ts": 1785399900000, "node": "livingroom", "temp": 21.4, "humidity": 41.2, "rssi": -58 }],
  "hourly":  [{ "hour": 1785396000000, "node": "livingroom", "tempAvg": 21.1, "tempMin": 20.8, "tempMax": 21.5, "humidityAvg": 41.0 }]
}
```

Оба массива приходят всегда: `samples` покрывает последние 30 дней, `hourly` —
всё, что старше. Клиент склеивает их сам. Кривые или перевёрнутые `from`/`to` —
`400`.

`GET /api/heating/stats/daily?from=…&to=…`:

```json
{ "days": [{ "day": "2026-01-10", "minutes": 312 }] }
```

День — календарный в часовом поясе малины (`Europe/Kyiv`), интервал горения,
пересекающий полночь, делится между сутками. Незакрытый интервал считается до `to`.

**WebSocket** `/ws/heating` отдаёт **тот же объект**, что `GET /state`, без
обёртки и без типа сообщения: раз структура одна, незачем плодить вторую. Первый
кадр уходит сразу при подключении, дальше — каждый тик, то есть раз в 10 секунд.
Клиент не шлёт в сокет ничего; все изменения идут через REST. Если сокет не
поднялся, интерфейс переходит на опрос `GET /state` раз в 10 секунд — поведение
неотличимо, просто чуть больше запросов.

**Конфигурация** — свои ключи в общем `server/.env`: `MQTT_URL`,
`MQTT_USER`, `MQTT_PASS`, `MQTT_TOPIC_PREFIX=heating`, `DATA_DIR=data`,
`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`.

**Telegram** — только исходящие уведомления плюс команда `/status`. Триггеры:

- датчик замолчал на 15 мин / вернулся;
- реле отвалилось по LWT / вернулось;
- переход на L1, L2, L3 и возврат в L0;
- главный датчик ниже 10 °C;
- **контакт замкнут 15 минут, а подача не выросла на 5 °C** — котёл не запускается:
  газ, блокировка, ошибка. Раньше это было неотличимо от «дом плохо греется», теперь
  диагноз однозначный;
- **котёл горит два часа, подача растёт, а комната не потеплела на 0.5 °C** — тепло
  уходит: открытое окно, воздух в системе, не хватает мощности;
- **дельта подача−обратка держится выше 30 °C дольше 10 минут при горящем котле** —
  похоже на остановку насоса котла или перекрытую ветку. Порог ориентировочный, его
  надо откалибровать по данным первой зимы;
- **нода насоса отвалилась** по LWT и вернулась;
- **нода насоса ослепла** (P1) и вернулась в норму (P0);
- **реле не слушается**: команда сервиса расходится с фактическим состоянием дольше
  30 минут. Обычно это значит, что кто-то нажал кнопку на коробке и забыл;
- **насос не выключился**: котёл стоит дольше, чем выбег плюс две минуты, а реле
  насоса всё ещё замкнуто — признак залипшего контакта или зависшего автомата;
- **насос не включился вместе с котлом** — тёплый пол греться не будет. Сообщение
  информационное: на батареи и на котёл это не влияет.

Антиспам: не чаще одного сообщения на тип в 30 минут.

## 10. Авторизация

Модуль живёт за общей auth-middleware хоста sweethome: те же сессии, API-токены
и роли, что у инвертора. `viewer` видит показания и графики; менять уставку и
настройки может только `admin` (гейт `requireAdmin` на PUT-маршрутах роутера).
Caddy не участвует: `rancho.network` уже проксирует на :3000 целиком.

## 11. Веб-интерфейс

Раздел `/heating/*` единого веб-приложения sweethome (Next 15, static export).

- **Главный экран:** температура главного датчика крупно, рядом — **температура на
  улице**, уставка с шагом 0.5, отдельные карточки котла и насоса (во время выбега —
  обратный отсчёт из `overrunLeft`), плашки уровней человеческим языком, три карточки
  комнат (t°, влажность, в сети / нет), график за сутки на uplot.
- **История:** графики за период, полосы работы котла и насоса, столбики «часов
  горения в день».
- **Настройки:** главный датчик, уставка, гистерезис, тайминги L1/L2, выбег насоса,
  летний прогон, Telegram.
- Шапка и навигация уже общие — раздел добавляется в системную навигацию рядом с Инвертором.
- Обновления по WebSocket.

### Состояния экранов

Каждое состояние описано явно, потому что «нет данных» и «ноль градусов» — это
разные вещи, и путать их в системе отопления нельзя.

| Ситуация | Что показываем |
|---|---|
| Снапшот ещё не пришёл | «Загрузка…», никаких нулей и прочерков в местах чисел |
| `GET /state` вернул ошибку | Красная строка с текстом ошибки как есть, остальное не рисуем |
| Комната офлайн или `temp: null` | В карточке «нет связи» вместо температуры; влажность скрыта, не обнулена |
| Главный датчик офлайн | Крупная цифра — «— °C», под ней `reason` от сервиса, объясняющий, что происходит |
| `desiredHeat: null` | Плашка «сервис не принимает решений» плюс `reason`; уставка остаётся видимой, но подписана «не применяется» |
| Нода котла офлайн | В карточке котла «Нет связи», это важнее любого уровня и перекрывает его |
| Нода насоса офлайн | В карточке насоса «Нет связи, тёплый пол не греется». Приписка, что на батареи это не влияет — иначе выглядит как отказ отопления |
| Нода насоса в P1 | «Не видит котла — остановлен», янтарным |
| Реле не совпадает с решением сервиса | Поверх плашки уровня — «Переключено кнопкой на коробке», янтарным. Вычисляется сравнением, отдельного флага в MQTT нет |
| Уличный датчик молчит | В строке улицы «— °C»; на работу отопления это не влияет, панику разводить не надо |
| Уровень L1/L2/L3 | Цветная плашка человеческим языком (см. таблицу ниже), а не буква уровня |
| Насос в выбеге | «Насос: работает — выбег, осталось 12:34», отсчёт из `overrunLeft` |
| Роль `viewer` | Все контролы `disabled`, сверху строка «Только просмотр: нужна роль admin» |
| Роль ещё не загрузилась | Считаем `viewer` — контролы заблокированы, пока не выяснится обратное |
| Настройка отвергнута сервером | Текст ошибки от сервера показывается дословно, поле не сбрасывается |
| В истории нет точек за период | «За выбранный период данных нет», пустой график не рисуем |

Тексты плашек уровня:

| Уровень | Текст | Цвет |
|---|---|---|
| `L0` | Работает в норме | зелёный |
| `L1` | Сервис не отвечает — реле греет само | янтарный |
| `L2` | Брокер недоступен — слепой цикл 15/45 мин | оранжевый |
| `L3` | Аварийная страховка по котельной | красный |
| нода котла офлайн | Нет связи с нодой котла | красный |
| `P0` | Насос следует за котлом | зелёный |
| `P1` | Не видит котла — остановлен | янтарный |
| нода насоса офлайн | Нет связи с нодой насоса | красный |

## 12. Матрица отказов

Одна таблица вместо трёх разбросанных описаний. «Тревога» — сообщение в Telegram,
дословные тексты в §13.

| Сценарий | Что делает система | Что видно в интерфейсе | Тревога |
|---|---|---|---|
| Замолчал не главный датчик | Ничего: на решение он не влияет | В его карточке «нет связи» | `silent:<room>`, при возврате `silent-ok:<room>` |
| Замолчал **главный** датчик | Через 30 мин сервис перестаёт командовать; нода уходит на L1, потом на L2 | Крупная цифра «— °C», плашка уровня, `reason` объясняет причину | `silent:<room>`, затем `level:L1` и `level:L2` |
| Замолчали все датчики | То же, что выше | Все карточки «нет связи» | По тревоге на каждый датчик плюс уровни |
| Сервис упал или перезапускается | Через 5 мин без команды нода уходит на L1 и греет сама по главному датчику | Страница не грузится либо WS отвалился | `level:L1` — но только когда сервис вернётся: слать её некому, пока он лежит |
| Малина умерла целиком | Брокер умер вместе с ней: нода на L1, пока помнит температуру, через 30 мин на L2 | Страница недоступна | Никакой: отправлять некому. Это дыра, и она закрыта только внешним мониторингом (§14) |
| Брокер упал, сервис жив | Сервис не может ни читать, ни командовать; нода через 30 мин на L2 | Данные застывают, WS живёт | `level:L2` после восстановления |
| Лёг роутер или WiFi | Нода котла теряет брокер, `reboot_timeout` у неё отключён — **не перезагружается**, работает по кэшу, затем L2. Нода насоса через 60 с уходит в P1 и **останавливает насос**: батареи греют, тёплый пол остывает | Страница недоступна извне | Нет |
| Пропало электричество | Оба реле нормально разомкнуты: котёл и насос стоят | — | Нет. При возврате питания — `boiler-online` и `pump-online` |
| Нода котла перезагрузилась | Реле поднимается разомкнутым, котёл решается заново за 10 с. Насос успевает уйти в P1, только если пауза дольше минуты | Короткий провал в «нет связи» | `boiler-offline`, затем `boiler-online` |
| **Нода насоса перезагрузилась или отвалилась** | Реле поднимается разомкнутым и ждёт состояния котла. Без брокера остаётся в P1, то есть выключенным | В карточке насоса «нет связи, пол не греется» | `pump-offline`, затем `pump-online` |
| **Нода котла жива, но насос её не слышит** | Насос остановлен, котёл работает штатно, батареи греют | Янтарная плашка у насоса | `pump-blind` |
| Нажали кнопку на коробке | Реле переключается и держится, пока автомат не поменяет решение | Янтарная плашка «переключено кнопкой» | Нет, если автомат вскоре передумает |
| Нажали кнопку и забыли | Держится сколько угодно — таймаута нет, как и у Tuya. L3 при этом работает | Плашка висит | `override-stuck` через 30 минут расхождения |
| **Оборвался кабель уличного датчика** | Ничего: он на отдельной шине 1-Wire и на L3 не влияет | «— °C» в строке улицы, дыра в графике | Нет |
| Отвалился датчик подачи или обратки | Управление не затронуто: на решение они не влияют. Молчат только диагностические тревоги | Пустая строка в карточке котла | Нет |
| Котельная ниже 8 °C | L3 замыкает котёл независимо от уставки | Красная плашка «аварийная страховка» | `level:L3` |
| Котельная выше 45 °C | L3 размыкает котёл независимо от всего, включая защиту горелки | Красная плашка | `level:L3` |
| Замкнули контакт, а котёл не запустился | Ничего: система своё сделала, проблема в котле | Подача не растёт на графике | `not-firing` |
| Котёл горит 2 ч, теплее не стало | Ничего: система работает штатно, проблема снаружи | Обычный вид | `no-progress` |
| Встал насос котла | Ничего автоматически; котёл сам уйдёт в защиту по перегреву | Резко разошлись подача и обратка | `no-circulation` |
| Насос не включился при горящем котле | Ничего автоматически — вмешаться может только человек | В карточке «Насос: стоит» при горящем котле | `pump-missing` |
| Насос не выключился после выбега | Ничего автоматически | «Насос: работает» при потухшем котле | `pump-stuck` |
| Упал Caddy | Отопление недоступно снаружи, но продолжает работать: сервис, брокер и нода не зависят от него | Сайт не открывается | Нет |
| Кончилось место на SD-карте | Запись в базу падает, управление продолжает работать: решение не зависит от истории | Графики пустеют | Нет. Закрывается внешним мониторингом (§14) |

Общий принцип виден по таблице: **отказ любой части системы делает управление
глупее, но не выключает его**, вплоть до полного обесточивания — там уже нечему
работать. Отдельно стоит насос тёплого пола: он единственный узел, отказ которого
не деградирует систему, а просто отключает одну её функцию. Дом остаётся тёплым за
счёт батарей.

Отдельно стоит признать неприятное: если малина умирает целиком, **сообщить об
этом некому** — Telegram-бот живёт на ней же. Эта дыра закрывается не внутри
проекта, а внешним наблюдателем, и он у нас уже есть (§14).

## 13. Тексты уведомлений

Дословно, чтобы не сочинять их заново при реализации. Все сообщения без разметки,
одной строкой. Антиспам — не чаще одного сообщения **на ключ** в 30 минут.

| Ключ | Когда | Текст |

| `level:L0` | Возврат в норму с любого уровня | `Всё в норме: отоплением снова управляет сервис.` |
| `level:L1` | Нода перешла на самостоятельную работу | `Сервис не отвечает — реле греет само по главному датчику.` |
| `level:L2` | Нода потеряла свежие температуры | `Брокер недоступен — реле перешло на слепой цикл 15/45 минут.` |

| `pump-missing` | Котёл горит, реле насоса разомкнуто | `Котёл греет, а насос тёплого пола не включился — полы греться не будут. На батареи это не влияет.` |
| `pump-stuck` | Котёл стоит дольше, чем выбег плюс 2 мин, а насос крутится | `Насос всё ещё крутится, хотя выбег давно закончился.` |
| `pump-offline` | LWT ноды насоса сказал `offline` | `Нода насоса отвалилась от брокера, насос остановлен. Тёплый пол остынет, батареи работают как обычно.` |
| `pump-online` | Нода насоса вернулась | `Нода насоса снова на связи.` |
| `pump-blind` | Нода насоса перешла в P1 | `Нода насоса не видит состояния котла и остановила насос. Тёплый пол остынет.` |
| `pump-ok` | Нода насоса вернулась в P0 | `Нода насоса снова видит котёл, выбег работает штатно.` |
| `override-stuck` | Команда сервиса расходится с состоянием реле дольше 30 мин | `Котёл замкнут, хотя автоматика этого не просит. Похоже, нажали кнопку на коробке и забыли.` |
| `override-gone` | Расхождение исчезло | `Котёл снова слушается автоматики.` |

Тревога о «холодно в доме» снимается только когда температура поднимется до
11 °C — то есть с гистерезисом в один градус. Иначе на границе 10 °C бот будет
слать сообщение каждые полчаса, и его перестанут читать ровно тогда, когда он
понадобится.

Команда `/status` в ответ присылает текущую сводку: температуры по комнатам,
уставку, состояние котла и насоса, уровень лестницы. Никаких управляющих команд у
бота нет — веб доступен снаружи, дублировать управление незачем.

## 14. Эксплуатация

### Сеть и адреса

| Устройство | Имя | Адрес | Как назначается |
|---|---|---|---|
| Raspberry Pi | `robot` | `192.168.1.112` | DHCP-резервирование по MAC WiFi на роутере |
| Датчик гостиной | `heating-livingroom` | DHCP | mDNS, резервирование не требуется |
| Датчик спальни | `heating-bedroom` | DHCP | то же |
| Датчик детской | `heating-kids` | DHCP | то же |
| Нода котла | `heating-boiler` | **резервировать** | DHCP-резервирование: нода критичная, адрес не должен уезжать |
| Нода насоса | `heating-pump` | **резервировать** | То же. Стоит дальше всех от роутера — уровень сигнала проверить на месте |
| Брокер | — | `192.168.1.112:1883` | Только LAN, наружу не проброшен |
| Модуль heating | — | общий процесс `sweethome`, `:3000` | Отдельного порта нет — тот же процесс, что инвертор |
| Снаружи | `rancho.network/heating` | — | Caddy, TLS (проксирует `:3000` целиком, как для инвертора) |
| Приватный вход | — | Tailscale | Уже настроен, отдельной работы не требует |

Ноды адресуются к брокеру **по IP, а не по имени**: mDNS-резолв при холодном
старте роутера может не подняться, а отопление должно.

### Права в брокере

Один пользователь на всё хозяйство — плохая идея: скомпрометированный датчик
сможет публиковать команды котлу. Пользователей шесть, права раздаются файлом ACL.

```
# /etc/mosquitto/acl

# Сервис — всё дерево целиком
user heating-service
topic readwrite heating/#

# Комнатные датчики — только своя ветка и только на запись
user node-livingroom
topic write heating/livingroom/#

user node-bedroom
topic write heating/bedroom/#

user node-kids
topic write heating/kids/#

# Нода котла: пишет своё, читает команды, конфиг и температуры комнат
user node-boiler
topic write heating/boiler/#
topic read heating/cmd/heat
topic read heating/cfg/#
topic read heating/livingroom/sensor/temperature/state
topic read heating/bedroom/sensor/temperature/state
topic read heating/kids/sensor/temperature/state

# Нода насоса: пишет своё, читает только состояние котла и свою конфигурацию
user node-pump
topic write heating/pump/#
topic read heating/boiler/sensor/heat/state
topic read heating/cfg/pump_overrun
topic read heating/cfg/pump_antiseize
```

В `mosquitto.conf` добавляется `acl_file /etc/mosquitto/acl`. Пароли — в
`/etc/mosquitto/passwd` через `mosquitto_passwd`, файл `600` и владелец
`mosquitto`.

### Бэкапы

Теряя `heating.db`, мы теряем историю и настройки — управление продолжит работать,
но уставку придётся выставить заново. Ежедневный бэкап по cron на малине:

```bash
0 4 * * * sqlite3 /home/pi/heating/server/data/heating.db \
  ".backup '/home/pi/backups/heating-$(date +\%u).db'"
```

Семь файлов по дням недели, перезаписываются по кругу — места не растёт. Команда
`.backup`, а не `cp`: копировать файл SQLite на ходу нельзя, получится битый снимок.

Отдельно, **вне малины**, должны лежать копии того, чего нет в гите:
`server/.env`, `firmware/secrets.yaml`, пароли брокера. Потеря SD-карты не должна
означать восстановление паролей по памяти.

### Замена ноды

Сгоревший датчик меняется так: прошить новую плату тем же YAML — имя, топики и
секреты те же, сервис ничего не заметит. Ни в какой конфигурации нода не
регистрируется: список комнат живёт в `ROOMS` сервиса, а не в брокере.

С нодой котла одна тонкость: **у нового `DS18B20` другой адрес на шине 1-Wire**.
Его надо взять из лога первой загрузки и вписать в `boiler-node.yaml` — отдельно для
датчика котельной и отдельно для уличного, шины у них разные. Пока адрес не совпал,
датчик молчит; для котельной это означает неработающий уровень L3, и проверять это
надо первым делом.

Нода насоса меняется проще всех: в ней нет ни одного датчика, только реле — прошить
тем же YAML, и всё. Менять можно в любой момент: пока новая нода не поднялась,
тёплый пол просто не греется, а на батареи и котёл это никак не влияет.

### Обновление прошивок

Только по OTA и **по одной ноде за раз**, с проверкой после каждой. Нода котла
обновляется последней и только тогда, когда есть возможность посмотреть на неё
живьём: ошибка в её автомате опаснее ошибки где угодно ещё в системе. В отопительный
сезон менять её прошивку без стендовой проверки нельзя.

### Диагностика

```bash
ssh pi@192.168.1.112 journalctl -u sweethome -f | grep heating   # логи модуля heating (общий процесс sweethome)
mosquitto_sub -h 192.168.1.112 -u heating-service -P '…' -t 'heating/#' -v   # весь обмен
mosquitto_sub -h 192.168.1.112 -u heating-service -P '…' -t 'heating/+/debug' -v  # логи нод
```

Логи нод идут в MQTT, а не по нативному API ESPHome: компонент `api` не
используется вовсе, потому что с ним нода перезагружается каждые 15 минут без
подключённого клиента.

### Внешний мониторинг

На малине уже работает `uptime-kuma`. Процесс `sweethome` (общий для инвертора и
модуля heating) уже покрыт существующей проверкой; отопление добавляет к
uptime-kuma одну новую проверку — живость брокера MQTT. Толку от них немного,
пока сама малина жива — но именно `uptime-kuma` умеет заметить, что она **не**
жива, и это единственный сценарий из §12, который система не в состоянии
сообщить о себе сама.

## 15. Тестирование

- **jest:** `thermostat.test.ts` (ядро, много кейсов — приоритет), `store.test.ts`,
  `mqtt.test.ts` на моке брокера, HTTP-тесты API и разделения ролей.
- **Настольный стенд — обязателен.** До установки на котёл собираем всё на столе,
  оба реле щёлкают вхолостую, и физически гасим по очереди сервис, брокер и WiFi,
  проверяя каждый уровень лестницы. L1 и L2 — код, который сработает один раз за
  зиму и обязан сработать; на живом котле его не отладить.
- **Сценарии насоса на том же стенде**, обе ноды рядом: включение одновременно с
  котлом; выбег ровно 15 минут; сброс таймера, если котёл включился посреди выбега;
  разомкнутое реле сразу после передёргивания питания ноды насоса.
- **Главная проверка после разделения нод — переход в P1.** Гасим брокер и смотрим,
  что нода насоса через 60 секунд размыкает реле и больше его не трогает. Потом
  поднимаем брокер и проверяем возврат в P0. Отдельно проверить, что залипший
  retained-`1` от умершей ноды котла насос не обманывает: именно от этого защищает
  проверка свежести.
- **Проверить, что нода котла публикует состояние регулярно**, а не только по
  изменению: `mosquitto_sub -t heating/boiler/sensor/heat/state -v` должен выдавать
  строку каждые 10 секунд при неподвижном котле. Без этого нода насоса будет
  сваливаться в P1 на ровном месте.

## 16. Критерии приёмки

Через месяц после переключения нужно уметь ответить, стало лучше или нет, не
ограничиваясь ощущением «вроде работает». Ниже — то, что можно проверить.

Критерии по насосу все до одного в желательных: он греет только тёплый пол, и его
отказ не повод откатывать систему.

**Обязательное. Не выполнено хотя бы одно — возвращаем Tuya-реле и разбираемся.**

| Критерий | Как проверить |
|---|---|
| Ни одного случая, когда дом остыл ниже 15 °C по вине системы | График главного датчика за месяц |
| Ни одного случая, когда котёл грел при недостижимой уставке дольше 4 часов подряд | `boiler_events`, длительность интервалов |
| Ложных тревог в Telegram — не больше двух за месяц | Переписка с ботом |
| Уровень L0 держится не меньше 99 % времени | Доля событий с `level != 'L0'` в `boiler_events` |

**Желательное. Не выполнено — повод подкрутить настройки, а не откатываться.**

| Критерий | Как проверить |
|---|---|
| Тактование котла не чаще 6 включений в час в установившемся режиме | `boiler_events` за характерные сутки |
| Отклонение главного датчика от уставки в пределах ±0.7 °C в установившемся режиме | График температуры против уставки |
| Часы горения за сопоставимый по погоде период не больше, чем было у Tuya | Сравнение с данными фазы 1 |
| Отвалов датчиков не больше одного на датчик в неделю | Тревоги `silent:*` |
| Насос ни разу не пропустил включение вместе с котлом | Отсутствие тревог `pump-missing` |
| Насос не оставался включённым дольше выбега плюс 5 минут при живой связи | Тревоги `pump-stuck`; интервалы в `boiler_events` при `pump_level = 'P0'` |
| Нода насоса провела в P1 меньше 1 % времени | Доля событий с `pump_level = 'P1'` |
| Веб открывается снаружи и показывает свежие данные | Руками, с телефона |

Данные для сравнения с Tuya берутся из фазы 1 внедрения: две недели, когда новые
датчики уже висели, а отоплением ещё управляло старое реле. Это единственный
момент, когда обе системы работают параллельно, и другого шанса собрать базу для
сравнения не будет — поэтому фазу 1 нельзя сокращать.

## 17. План внедрения

1. **Только датчики.** Три ноды висят рядом с Tuya-датчиками, ничего не
   коммутируют. Одна-две недели сверяем графики и ловим отвалы WiFi. Отоплением
   всё это время рулит Tuya.
2. **Обе ноды на столе, рядом.** Прогнали все четыре уровня котла и оба уровня
   насоса — выбег, сброс таймера при повторном включении, включение на старте,
   летний прогон и, главное, переход в P1 при погашенном брокере. Реле щёлкают
   вхолостую, без нагрузки. Здесь же замерили клеммы котла мультиметром,
   посмотрели шильдик насоса.
3. **Замер связи на обоих местах.** Отнести собранные ноды в котельную и к насосу,
   полчаса посмотреть `RSSI`. Ожидаем, что всё нормально: соседние Tuya и малина там
   работают. Проверяем ровно затем, чтобы не выяснять это после сборки коробок.
4. **Уличный датчик.** Протянуть кабель, повесить датчик, убедиться, что вторая шина
   1-Wire читается и не мешает первой.
5. **Переключение.** Собираем обе коробки, перекидываем нагрузки: сухой контакт
   котла — на ноду котла, питание насоса — на ноду насоса. Оба Tuya-реле **не
   выбрасываем** — в ящик, как готовую замену, если своё подведёт в январе.

Параллельно старое и новое реле на одни клеммы не вешаем: два сухих контакта в
параллель дают «или-или», и Tuya включит котёл тогда, когда наш решил не греть.
С насосом ещё жёстче — там параллельное включение двух реле на одну фазу
недопустимо.

Порядок переключения не критичен: худшее, что даёт промежуток между двумя
монтажами, — временно не греющийся тёплый пол. Если работы растягиваются на разные
дни, логичнее начать **с котла**: он важнее, а полы подождут.

Инфраструктурная подготовка: `mosquitto` из apt на Pi (слушает `127.0.0.1` и
LAN-интерфейс, пароль, без анонимных подключений, `persistence` включён),
`Caddyfile` переезжает в репозиторий (`infra/Caddyfile`) и деплоится вместе с
кодом, systemd-юнит `heating.service`, `deploy.sh` по образцу инвертора (сборка
локально → rsync → restart).

Отдельная зависимость: **эндпоинт `GET /api/authz` в `inverter-monitor`** (§10).
Это чужой репозиторий, поэтому изменение идёт своим MR и должно быть задеплоено
раньше, чем на `/heating` появится что-то, кроме заглушки.

## 18. Риски

- **Первая зима на самоделке.** Отсюда лестница деградации, уведомления и
  сохранённое Tuya-реле.
- **Ошибка в `lambda` реле-ноды опаснее ошибки в сервисе.** Обновляется по OTA, но
  проверять — на столе.
- **SD-карта малины** остаётся общей точкой отказа с инвертором. Отопление её не
  ухудшает, но забывать не стоит; `uptime-kuma` уже наблюдает.
- **Клеммы котла до сих пор не измерены.** Реле выбрано с запасом по напряжению,
  но корпус и разводка зависят от результата.
- **220 В в сборке.** До появления насоса это был проект «на столе», теперь в
  коробке живёт сетевое напряжение рядом с контроллером. Отсюда требования §7:
  предохранитель, разнос цепей, винтовые клеммники, гермовводы. Выбран вариант без
  щитка, поэтому компоновку внутри коробки надо продумать заранее — рейка её
  больше не навязывает.
- **Холодный пол при отказе связи.** Нода насоса, потерявшая котла из виду,
  останавливает насос. Дом при этом греется батареями, но комнаты с тёплым полом
  станут прохладнее — тем заметнее, чем дольше длится отказ. Это осознанный размен:
  крутить насос вслепую значило бы жечь около 1.2 кВт·ч в сутки без всякой пользы,
  потому что без горящего котла в контуре всё равно нет тепла.
- **Две коробки с 220 В.** Разделение нод удвоило количество мест, где живёт сеть,
  и питание ноды котла от `HLK-5M05` вместо USB-зарядки это закрепило. Требования §7
  распространяются на обе одинаково. В коробке котла есть своя особенность: ошибка
  монтажа там бьёт не по насосу, а по плате управления котла, которая ждёт на клеммах
  24 В.
- **Связь в котельной.** Обе силовые ноды стоят в полуподвале среди металла. По
  факту связь там нормальная — рядом работают Tuya, малина и счётчики, — так что
  риск невысокий. Но если она всё же будет мигать, штатным станет аварийный режим:
  отопление на L1, пол выключен, история дырявая. Кабель туда не протянуть, так что
  лечить пришлось бы антенной или точкой доступа поближе.

## 19. Вне скоупа v1

Сознательно отложено: расписание по времени и дням, режимы «Дом / Отъезд / Буст»,
Home Assistant, управляющие команды в Telegram-боте (только `/status`),
вынос общей шапки в отдельный пакет.

Отдельно про уличный датчик: в v1 он **только измеряет**. Погодозависимое
регулирование — когда уставка теплоносителя или гистерезис ведут себя по-разному в
+5 и в −15 — вещь полезная, но это отдельная фича со своей кривой отопления и своей
спекой. Сначала соберём данные за зиму, потом решим, нужна ли она вообще.

## 20. Открытые вопросы

- **Подтвердить исполнение котла и напряжение на клеммах.** По документации ждём
  24 В и ~10 мА, беспотенциальный вход (§7) — но у исполнения `WH0` термостат
  подключается к фазе. Посмотреть шильдик и померить напряжение на разомкнутых
  клеммах: 24 В — слаботочная коробка, 230 В — вторая сетевая как у насоса.
- Как назвать три комнаты в топиках и интерфейсе (`livingroom` / `bedroom` /
  `kids` — предположение).
- Мощность насоса по шильдику — от неё зависит номинал предохранителя и сечение
  провода. Предполагаем 30–100 Вт.
- **Фактический `RSSI` в котельной и у насоса.** Ожидаем нормальный: рядом работают
  Tuya, малина и смарт-счётчики. Замерить при сборке — чтобы знать запас, а не чтобы
  выбирать плату.
- Где именно вешать уличный датчик: нужна тень, желательно северная стена, подальше
  от окон, вытяжек и наружных блоков кондиционеров.
